# Go 配置发布闭环

Node 管理服务继续保存并校验配置；开启快照发布后，管理台的“发布已保存配置到 Go”会自动读取已保存的源配置、生成不含凭据的快照、原子替换、携带运行版本执行热更新，再读取 Go 核对生效版本。无需在每次保存后手工运行导出器。保存与发布是两个明确动作：未保存草稿不会下发，保存成功也不等于 Go 已生效。

## 启用

先按 NATIVE_FEATURES.md 导出一次 bootstrap 快照并启动 Go。在同机 Node 管理服务环境中配置：

```text
AMR_GO_ADMIN_URL=http://127.0.0.1:8791
AMR_GO_ADMIN_TOKEN=<与 Go auth.json 的 adminToken 相同，使用本地受保护凭据>
AMR_GO_RUNTIME_CONFIG=<Go --runtime-config 指向的同一个文件>
ADMIN_TOKEN=<原有管理台凭据>
```

管理服务需要快照目录写权限，Go 只需读取。整个目录共享，不能只挂载单个快照文件，否则原子替换可能不可见。源 router.json 与快照必须是不同文件；每个快照只允许一个管理发布者。不要同时运行 CLI 导出器、直接 Go reload 或其他文件写入程序。未配置 AMR_GO_RUNTIME_CONFIG 时保持原有适配器模式。

1. 在现有管理页面修改、预览并保存配置。
2. 概览的“实验 Go 核心”显示已保存与 Go 生效版本是否一致。
3. 点击“发布已保存配置到 Go”。请求保留 If-Match 并发保护，旧运行版本拒绝发布。
4. 页面自动查询确认。“已加载当前保存的配置”表示生效 revision 与保存 revision 一致；发布期间又有人保存时可能仍显示未同步，应检查新差异后再次发布。

## 失败与恢复

源配置或快照生成失败不替换原快照。Go 拒绝且确认仍运行旧代时，管理桥恢复旧快照，原有请求继续使用旧配置；源 router.json 保留，页面仍显示未同步。发布请求超时先读取生效代，确认已应用则完成，确认未应用则恢复旧快照，不盲目重复 POST。

发布前创建 runtime.json.pending 独占事务记录，包含旧快照和目标 revision，无模型凭据或请求正文。无法确认、管理进程退出或写入中断时保留记录，Go 启动会拒绝加载待确认快照。Go 仍运行时，在管理台查询最新版本并再次发布，会先按生效代核对和恢复上次事务；若遇其他发布者改动，保留记录并报错。

如果 Go 已停止而无法读取生效代，先停止 Node 管理发布者与 Go，执行离线恢复，然后重启 Go、管理服务并核对状态：

```sh
node go-core/compat/recover-publication.mjs --offline-restore-previous /absolute/path/runtime.json
```

此命令明确恢复上次发布前快照，不恢复源 router.json。源与生效版本不同可在核对后重新发布。不要直接删除 pending 标记。凭据轮换仍是独立受保护 auth.json 操作；如与配置同时改动，凭据回滚需要同步恢复对应备份。本轮不自动管理凭据文件。

## 验证边界

单元用例覆盖陈旧版本、明确拒绝、响应丢失、中断恢复、串行并发和无效源配置。真实 Go 进程演示覆盖自动快照发布、鉴权轮换、SSE 与重启账本恢复；真实 Node 管理接口演示覆盖 cookie 登录、保存后未同步、发布后同步、陈旧拒绝和坏配置保留原代。容器部署见 DEPLOYMENT.md。本阶段不切换生产流量，也不代表一小时稳定性或真实 Python/模型环境验收完成。
