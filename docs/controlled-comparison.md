# 真实业务效果对比

目前已交付数据检查与离线对比工具，尚未运行受控业务实验，也未证明线上收益。管理端“效果洞察 → 真实效果对比”可导入脱敏矩阵并下载结果；原始题目、回答和凭据不要上传。

## 先冻结业务口径

由业务样本负责人提供代表任务及每类任务的成功判据。按完整会话或独立任务组划分 train / validation / test，保留数据来源、采集日期、业务类别及脱敏记录。同组不得跨集合，测试集不得用于选模型、设门槛或调路由。

开始采集之前，在独立实验目录保存 `protocol.json`，记录任务范围、分组方法、成功标准、当前路由配置哈希、候选模型版本、推理参数、成本币种，以及业务接受的质量非劣界限、成本目标和 P95 时延上限。这些阈值需要业务输入，当前不填造数值。修改方案须新版本并重新划分测试数据。

## 采集与比较

按照 [数据契约](routing-matrix.md) 为同一测试任务采集完整候选观测。记录任务级成功与判断依据、包括失败重试和工具执行的实际总费用、端到端耗时，以及可追溯的证据引用。固定单模型基线在 validation 集选择；当前路由和候选策略在看测试结果之前冻结。任务执行顺序随机交错，控制模型版本、推理参数与流量时段，不能把后补的非同期样本视为严格同条件。

至少 30 个独立测试组是分析下限，并非样本量充分性的保证。先用先导样本估计方差，再根据最小关注效果确定样本量。工具进行配对组级 bootstrap，报告任务成功率、成功任务成本及耗时；候选覆盖不完整、估算成本、合成数据或测试组不足会阻止效果声明。

管理端限制 2 MB、200 个任务、6 个候选、1200 条观测、2400 条策略选择，固定 500 次 bootstrap。更大的矩阵使用：

```sh
node scripts/analyze-routing-matrix.mjs --input matrix.json --out comparison-report.json
```

离线通过后，依据已冻结的业务界限评审是否开展小流量随机对照。预先确定分组单位、暴露比例、观察时长、停止规则和回滚配置；样本未齐或阈值未定时不启动。线上启用是独立动作，导入分析不会修改路由、训练模型、调用上游或产生自动发布。

## 现有证据的边界

生产日志主要记录已选模型，缺少未选候选的反事实观测；HTTP 成功不等于任务成功。历史 Judge 跑分缺少模型版本和题目内容版本，不能替代业务实验。当前准备状态明确保留这些阻塞项，等待代表业务任务与成功标准。
