# Auto 核心 Go 迁移路线

用户于 2026-09-09 确认：在独立分支逐步做到可替换现有核心服务，本轮先交付可运行的核心与 Node 对照验证，不直接切换生产。

基线为 `v0.14.5`，提交 `1aa23e49646b8d7e9604707be1c740091687f092`。开发分支为 `codex/go-core-migration`；正式 Node 发布线继续独立维护，未达到切换条件前不合并为生产实现。

## 目标职责

| 组件 | 长期职责 |
|---|---|
| Go 核心请求服务 | 接入鉴权、请求校验、规则与选模、额度预占、上游转发、SSE、超时取消、失败回退、计量事件 |
| 管理台与控制接口 | 沿用现有前端；保存草稿、影响预估、审核发布、下发版本化策略，不必随核心一起重写 |
| Python 分类/学习/评测 | 保留既有模型及数据生态，以明确 HTTP/离线文件合同衔接 |
| 运行状态 | 明确一个权威写入方；按阶段迁移健康、并发、预算、会话和日志，不能两套实现独立记账后直接相加 |

初期保留 Node 规则适配器是迁移过渡，不是长期让每个请求都必须跨语言调用。后续把 L1 规则与容量估算迁到 Go，并保留 Python L2 接口；管理接口也只有在维护收益明确时才迁移。

M1 尚未实现 M2/M3 的完整生产行为。Go 返回了回退顺序，不代表实验执行器已经有生产重试；能输入健康/市场快照，不代表已接入线上动态状态；通过合成语料，不代表业务效果已经验证。

## 性能对照怎样避免误判

先把目标写成：请求/秒、同时在线 SSE 数、请求和响应体分布、允许的网关附加 P95/P99 延迟、CPU/内存配额、错误率和完整交付率。

至少分别测三组：

1. 同一特征输入的纯选模内核，明确排除分类、序列化和网络的范围。
2. 可控模拟上游的完整网关链路，包含输入解析、连接、转发和持续流量下的排队；同时测短请求与长 SSE。
3. 代表真实任务的完整链路，保持模型与策略一致，分开统计网关开销、分类复核、上游排队与模型推理。

正式比较不把带 Node 适配器的 Go 实验链路当成最终 Go 架构，也不能拿 Go 的纯内核时间与 Node 的整条请求时间比较。单次突发排空、功能测试通过、或 Go 原生并发支持都不能证明线上容量优势。

## 分支交付和发布边界

- M1 可以提交并推送迁移分支，CI 只运行本地模拟与离线检查，不部署。
- 当前不修改 package 版本、生产 Compose 或线上配置，不创建伪装成正式版本的发布标签。
- 合并现有 Node 改动时重跑差分语料；允许扩大语料，不通过放宽关键结果比较来掩盖差异。
- 达到生产候选阶段后，再沿用项目正式版本、镜像 revision、发布测试、备份和线上验收要求。
