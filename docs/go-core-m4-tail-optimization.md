## 实现与依据

本地分析组件 CPU/分配采样显示：有限词扫描仍包含逐字符解码、大小写折叠和映射查找；`jsLen` 会将字符串转换为 rune 数组及 UTF-16 数组，`regexText` 则对普通中文输入也重新编码整段文本。该采样覆盖短文本和长历史组件，不包含 Node adapter、HTTP 或预算锁等待，不能将其解释为完整网关尾延迟的根因证明。

- UTF-16 长度直接遍历计数：BMP 字符一个单元，补充平面字符两个单元，避免临时数组。
- 正则适配先扫描是否需要转换；普通 BMP 文本直接复用字符串。遇到补充平面字符或异常 UTF-8 才创建输出，继续保持原先的代理单元映射和替换字符行为。
- 有限词规则在编译时建立可能的 UTF-8 首字节集合，包含 Unicode SimpleFold 全部等价起始字符。扫描时跳过不可能开始匹配的字节，之后仍沿用原匹配顺序和完整匹配计数。包含 RuneError 起始字符时保留逐 rune 扫描，避免异常 UTF-8 的边界变化。

运行时账本、审计、同步落盘、重试、配额、Node adapter 和模型策略均未修改。没有截断历史、删减信号或缓存请求文本。

## 同机对照方法

工作流 `tail-optimization` 固定上一轮优化提交 `cd02f356d165c5bf1ddd73048c52bc4167fb73d8` 为基线，在同一个 Linux runner 构建两版并分别执行组件基准及完整网关实验。每版使用同一当前测试程序，包含 direct、Node、Go 路径，在三轮内轮换路径顺序。

两版均为完整服务组 1 CPU / 512 MiB，150/300 RPS、每档三轮、10 秒发起窗口，短文本/长历史/工具/图片各占四分之一；另有 32 路、60 秒 SSE。资源口径为 cgroup 内 Go runtime、Node adapter 与 Node 管理服务总和。采样峰值包含页缓存，不是单进程 RSS。

前后阶段固定顺序运行，属于同机工程对照，并非随机交错的统计试验；Node/direct 对照用于观察环境漂移。Node 异步账本和 Go 同步落盘的语义成本仍不同，不把两者差距归因于语言本身。合成负载和分钟级 SSE 不能替代真实业务、生产 SLO 或长时间稳定性验收。
