# Go 原生请求链路迁移与回归

本轮已将每请求的配置默认值、任务质量数据和决策输入构建迁到 Go，并增加本地配置快照入口。使用本地快照时无需启动 Node 配置适配器；管理端配置校验、成本派生与 Python 分类服务仍保留。本地、Linux 竞态与差分验证通过。容量回归全部 108,234 个请求完成，无错误、无未发起计划；新版直接 300 RPS 首轮 P95 为 39.85 ms。常规 300 RPS 的组合 CPU/采样内存较旧版下降约 25%/38%，但 P95 从 48.24 升至 51.33 ms，不能宣称延迟全面改善。生产未切换。

## 实测结果

以下均为同一 runner、每组 1 CPU / 512 MiB、关闭采样的合成负载结果。旧版保留每请求 Node 适配器，新版以本地快照运行且不启动适配器；两者均包含 Node 管理进程。分位数不能相减当作网关附加分位数。

| 常规档位与路径 | 完整/计划 | P95/P99 ms | 平均 CPU 核 | 采样内存峰值 MiB |
|---|---:|---:|---:|---:|
| 150 RPS 旧 Go | 4500/4500 | 27.64 / 61.55 | 0.441 | 70.07 |
| 150 RPS 新 Go | 4500/4500 | 34.05 / 73.44 | 0.329 | 44.84 |
| 150 RPS 同阶段 Node | 4500/4500 | 17.04 / 23.08 | 0.509 | 86.78 |
| 300 RPS 旧 Go | 9000/9000 | 48.24 / 212.09 | 0.785 | 105.48 |
| 300 RPS 新 Go | 9000/9000 | 51.33 / 122.15 | 0.590 | 65.28 |
| 300 RPS 同阶段 Node | 9000/9000 | 54.82 / 96.04 | 0.932 | 138.93 |

旧、新常规流程各完成全部 40,608 个请求，均无错误或未发起计划。新版 300 RPS CPU 下降约 24.9%、采样内存下降约 38.1%，P99 下降约 42.4%；但 P95 上升约 6.4%。150 RPS P95 上升约 23.2%（增加 6.41 ms），不能用资源节省掩盖这一观测退化。固定先旧后新的时序和单个 runner 不足以确定这些延迟变化的稳定幅度或根因，目标环境须继续跟踪。

新版常规 300 RPS 三轮 Go P95 为 86.47、43.34、37.97 ms；旧版为 92.12、42.29、41.20 ms。新版阶段 Node P95 为 38.70、40.62、80.61 ms，合并为 54.82 ms；旧版阶段 Node 合并 P95 为 70.69 ms，说明对照自身也在波动。不能仅凭新版 Go 汇总 P95 略低于 Node 就宣称稳定领先，且新版 Go P99 仍高于同阶段 Node。

各常规路径 32 路 60 秒 SSE 全部完整。旧 Go 首包 P95 为 84.88 ms，新 Go 为 59.02 ms；新版阶段 Node 为 82.61 ms、direct 为 23.25 ms。本轮没有流式完整性退化。

|---|---:|---:|---:|---:|

| 第二轮 | 3000/3000 | 37.96 | 65.40 | 0 |

启动组三个路径及预检/短 SSE 共 27,018 个请求全部完整；Go 三轮合并 P95/P99 为 39.33/81.69 ms，同阶段 Node 为 91.91/173.44 ms。本轮首次观察到该新版启动检查无未发起计划，但第三轮 Go P99 仍有 207.70 ms 长尾。此轮没有旧版同次冷启动对照，不与上一轮 873/763 ms 作因果比例比较，也不把一次通过当作长期启动保证。

结论：原生请求迁移可保留，资源占用和本轮启动完整性有正面证据；常规低档延迟、目标部署环境、真实业务分布、小时级稳定性和正式 SLO 仍需验收，尚未达到直接替换生产入口的条件。

## 实现与边界

- `internal/features` 按配置代解析默认值、任务偏好、相对质量上限、模型质量和子任务样本；请求在 Go 中构建原有版本化决策输入。保留缺失/空值与显式零值的区别、数字字符串及思考参数语义。
- 热更新发布完整配置代；在途请求及语义重分类继续旧代，各请求的可变结果相互隔离。无效快照保留原代，账本、计费和审计耐久规则不变。
- `export-runtime.mjs` 从经过现有 Node 校验与成本派生的配置生成白名单快照，`--runtime-config` 本地加载；不把全部管理配置、凭据、端点或请求正文传入特征配置。
- 网络配置源只在启动/热更新时使用，新协议不再依赖适配器保留 64 代历史。早期请求适配器路径保留为兼容对照，未删除 Node 管理端或 Python 服务。

使用方法及本地快照的显式导出/发布步骤见[原生决策输入说明](../go-core/NATIVE_FEATURES.md)。本地快照模式不自动把管理端保存操作视作已生效，须重新导出后执行 CAS 热更新并核对版本。

## 容量回归方法

[容量工作流](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34448567561)执行代码为 `87a1313bbe3447a4218865adb230dd77c3309183`；基线为 `cf991161186dd17d2452773060a426e46bccef7c`，含上一轮账本与审计合并提交。

同一个 Linux runner、同一镜像与语料，每组硬配额 1 CPU / 512 MiB，Go 使用自动执行槽设置；模拟上游，不调用真实模型。按旧版常规、新版常规、新版直接启动 300 RPS 的顺序运行，关闭采样。

常规流程为 150/300 RPS 各三轮、每轮 10 秒，以及各路径 32 路 60 秒 SSE；启动检查为新进程、新账本，直接 300 RPS 三轮，另做 2 路 2 秒 SSE。均保留四类输入各一次预检，不能称为零预热。

旧 Go 仍调用每请求适配器，新 Go 使用本地快照且不启动适配器；两者资源统计均包含 Node 管理进程。常规阶段相同配额，但固定先旧后新的顺序不能排除主机时序波动；启动阶段没有同次旧版冷启动对照，不能据此计算因果改善比例。延迟分位数仅覆盖完整请求，错误和未发起计划必须另列。cgroup 采样峰值内存不是 RSS。
