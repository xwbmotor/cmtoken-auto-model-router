## 诊断依据

重新解析第三轮保留的 Go 自动调度原始 trace（CI `34432139195`），按请求协程的阶段和状态转换拆分启动区间。预检首条请求之后 19–24 秒的五秒窗口覆盖第一轮 300 RPS 启动；该窗口内观察到：

- 单次账本锁等待最长 221.05 ms，调用栈落在 `Ledger.Settle`；`Snapshot`、`Reserve` 也有约 180–200 ms 的等待。
- 单次 `fsync` 的 syscall 状态最长 34.70 ms，位于 `Ledger.commit`；多个协程排队使总等待远大于一次同步耗时。
- 可运行协程等待调度最长 88.45 ms。不能把全部长尾归为磁盘硬件延迟，更不能用 trace 的采样开销下延迟作为正式容量指标。

这证明了读写共用锁参与排队，尚不证明它是唯一原因。解析脚本及结果保存在 `data/go-migration/inspect-cold-trace.mjs`、`cold-trace-waits.json`；原始 trace 保存在 `runtime-profile-34432139195/capacity-profile-auto.json.profiles/runtime.trace`。

## 最终实现边界与正确性

最终候选为账本和审计各设一个写入协程。每个队列上限 256，每次最多取 64 个已经排队的操作，没有定时等待凑批；空闲时立即处理单笔。预算校验和试算按顺序执行，多个调用可共享一次文件写入与 `fsync`，每个调用均在所属批次同步成功后才收到成功结果。快照仍使用锁，不暴露暂存状态。WAL 的逐记录格式、校验和、序号及恢复规则，以及审计逐行 JSON 格式不变；两个文件仍是各自独立的提交，不构成跨文件原子事务，也不改变已发出响应无法撤回的约束。

同步或写入失败会撤销该批的暂存快照、尝试记录、序号及导入状态；本应成功的调用统一得到错误，写入器进入失败关闭状态。关闭入口后先排空已接收操作，再释放文件锁。失败返回或进程崩溃后，磁盘可能已存在部分或全部未确认记录，恢复仍按完整合法前缀处理，不能凭错误返回认定预留从未存在。

新增测试覆盖合并同步与原子预算、落盘前不得返回成功、64 笔批次上限、关闭排空、同步失败整批报错与状态撤销；原有强杀恢复测试增加 32 个并发预留后强杀的场景。审计另覆盖批次上限、关闭排空、逐行完整性、同步失败禁止确认、写入失败后停止继续写入并使运行时失败关闭。既有跨日、重启恢复、失败关闭、预算竞态与账本往返测试继续保留。

## 同机对照方法

- 旧版：`5a97c1de583757a61d48453f34ab869e722eba57`；账本与审计合并提交候选：`189d51b3821e236aaf77bddb4b05067dbea1016b`。
- 单个 Linux runner 内按“旧 1、新 1、新 2、旧 2”交错运行，每次创建全新进程、独立账本与审计文件。每次直接 300 RPS、3 轮、每轮 10 秒；保留四类输入各一条预检。因此这里指“不经过 150 RPS 阶段”，不是零请求预热或清空操作系统页缓存。
- 每组硬配额保持 1 CPU / 512 MiB；Go 自动调度，包含 Go、Node 适配器与 Node 管理进程。Node 对照沿用相同代码和配置。
- 四次无采样测试后，对候选执行 150/300 RPS 常规检查和各路径 32 路 60 秒 SSE；最后另启一个新进程进行 trace 诊断，采样结果不混入容量分位数。
- 完整请求/计划数、发压器丢弃、第一轮 P95/P99、后两轮、CPU、内存及 Node/direct 对照同时报告。工作流运行成功不等于容量达标。
