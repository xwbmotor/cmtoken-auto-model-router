# 路由设计说明

路由需要先确定“哪些模型能处理这个请求”，再决定“其中哪个更合适”。模型质量分、价格和时延是决策输入，并不是服务对每个回答的保证。

本文描述 v0.14.8 的主要行为。Go 执行业务请求，Node 负责配置和结果记录；更细的字段及实验实现见 [路由约束](router-foundations.md)和 [Go 开发说明](../go-core/README.md)。

## 从请求到响应

1. 读取请求并识别任务、难度、工具及输出格式等要求。容量估算包含 system、历史消息、工具定义和输出预留，是启发式估算，不是模型 tokenizer 的精确结果。
2. 根据启用状态、调用方权限、能力、上下文容量和质量门槛筛选候选。显式点名也要通过权限、能力和容量检查。
3. 如策略要求，进行小模型或大模型语义复核。仅在允许采纳的模式、灰度范围和置信度条件下改变分类结果。
4. 对合格候选评分，再处理任务偏好、会话黏性和本进程并发限制。这些机制不能把已被排除的模型重新放回候选池。
5. 发起上游调用，转发 JSON 或 SSE。遇到符合重试条件的故障才重试，所有尝试在最终记录中关联到同一请求。

## 评分与质量约束

评分综合质量、用户成本、平台资源成本、时延、不确定性、自建偏好和健康惩罚。实际权重来自配置，不能把文档里某个历史权重或固定模型排名当作当前规则。

用户成本与平台成本是不同指标。前者反映用户使用模型的价格，后者反映部署资源相对于吞吐的消耗；平台成本的计算使用总设备资源除以“实例数 × 单实例输出 TPS”。详见 [负载与评分](model-load-and-scoring.md)。

任务偏好仅在允许的分差内生效。正常重试和会话黏性仍受合格候选范围约束。没有模型达到质量门槛时默认失败；只有明确开启质量降级才可放宽相应条件，并记录降级原因。这不能放宽租户权限、模型能力或上下文约束。

历史评测分数可能缺少模型版本或完整题目来源。管理端的分数和模拟结果用于解释当前配置，真实业务质量与成本收益仍需代表性任务的受控比较。

## 语义复核与回答评审

语义复核判断请求属于什么任务、需要多大能力。`shadow` 保留初始决策并异步记录复核结果；`active` 允许在置信度和灰度条件满足时采纳。小模型与规则分歧并不说明谁正确，需要人工标准或可信标注来判定。

过去文档中的“500 条、5%、7 天”等是阶段性观察建议，不是自动切换的充分条件。切换前应检查代表性样本、错误分类、额外时延和费用，并准备恢复原策略的方法。参数含义以配置校验和管理端说明为准。

Judge 在回答完成后抽样检查质量。它与语义复核分别记录，可能失败，也可能受采样或预算限制。Judge 分数不会自动覆盖模型质量配置，离线学习程序也未作为当前生产选模策略启用。

## 费用、失败与恢复

已验收的 Go 生产部署关闭预算保护，使用 Node 费用观察。它记录请求和多次尝试的费用，不表示对调用方上游账户余额做了硬限制。Go 独立持久化账本属于另一路实现，其测试结果不能直接套用到这一部署。

鉴权、权限和请求类错误不应污染所有调用方共享的模型健康。可重试的供应商故障、超时与客户端取消分开处理；收到流式片段也不等于完整交付。

配置由 Node 校验并向 Go 发布。发布结果不确定时要先完成对账；旧配置实例在仍有后台复核时继续存活，排空后再释放。服务停止时先让 Go 排空，再关闭 Node 与分类器，避免丢失结果回传。

## 如何验证效果

功能测试证明指定场景的行为，模拟压测用于比较处理开销，真实任务对照才用于判断质量与业务成本。三类结果分别记录。开始业务对照前，先确定任务、成功标准和可接受的质量、费用及延迟范围，参见 [受控比较](controlled-comparison.md)。
