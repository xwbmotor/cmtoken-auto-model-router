# 路由设计说明（部署团队必读）

> 回答最常见的三个问题：为什么大部分请求默认选 DeepSeek？分流是怎么工作的？什么条件切换语义复核生效？

## 1. 为什么 10 类任务大多选 deepseekv4-flash？

**不是配置偏向，是三维评分的数学结果。**

评分公式（每个候选模型算一遍，取最高分）：

```
score = 1.0 × quality      ← 该任务类型的实测质量分
      − 0.22 × costIndex   ← 相对成本（越大越贵）
      − 0.12 × latencyIndex ← 相对时延（越大越慢）
      − uncertainty        ← 未验证模型惩罚
      + selfBonus          ← 自建模型加分
      − livePenalty        ← 实时健康惩罚（错误/慢）
```

deepseekv4-flash 当前三维全占优：

| 维度 | deepseekv4-flash | qwen36-35b | hy3-preview |
|---|---|---|---|
| 质量分（coding） | **0.93** | 0.77 | 0.92 |
| 成本指数 | **0.12**（最低） | 0.20 | 0.22 |
| 时延指数 | **0.21**（最快） | 0.40 | 0.63 |
| 实测均延迟 | **9.1s** | 17.3s | 27.5s |

质量顶格 + 最便宜 + 最快 → 三项相加数学上必然第一。**这正是路由器按设计工作的表现，不是故障。**

## 2. 那分流什么时候发生？

分流不靠硬指定，靠**容差分流（taskPreferences）**：某模型与最优模型的分差 ≤ 容差时，选该模型。逻辑：

- 该模型在这类任务上质量分本就接近最优（差 ≤ 0.03）；
- 分流后质量无实质损失，但可利用该模型的并发余量；
- 一旦预算压力上升（成本权重最高放大 3 倍），分差拉大超容差，**自动回落最优模型**——预算保护语义天然成立。

当前配置（config/router.json `routing.taskPreferences`）：

| 任务 | 分流到 | 容差 | 依据 |
|---|---|---|---|
| extraction（结构化提取） | qwen36-35b | 0.035 | qwen 质量分 **0.92 全场最高**（dsf 0.90），差值被成本/时延淹没 |
| creative（内容创作） | qwen36-35b | 0.035 | qwen 0.89 并列最高（dsf 0.88） |

注意：coding/reasoning 分差 0.20/0.08 远超容差，维持 deepseekv4-flash——**分流只发生在质量不打折的区间**。若 qwen 的 coding 质量分未来实测上调，容差机制无需改动即可自动扩大分流范围。

## 3. 语义复核 shadow → active 切换条件（量化）

shadow 模式只记录小模型与规则层的分歧，不改变路由。切换 active 的门槛：

- 复核成功样本 ≥ **500 条**
- 分歧率 ≤ **5%**（分歧 = 小模型与规则层任务类型判断不一致）
- 错误率 ≤ **1%**（分类器服务故障/超时占比）
- 观察期 ≥ **7 天**（覆盖工作日/周末流量模式）

切换方式：管理面板「语义复核运行方式」→ 正式采用，或 `config/router.json` → `semanticRouter.mode: "active"`。回滚：改回 `shadow` 并 reload，即时生效（无需重启）。

切换后出问题时：决策日志（data/decision-log/）记录了每次路由的 `semanticReview` 字段，可精确复盘哪些请求受复核影响。

## 4. 面板数据与决策日志的对应

| 面板卡片 | 数据来源 |
|---|---|
| 语义复核分歧 | counters.semantic.disagreed / succeeded |
| 分类器自身指标 | 分类器服务 :8788 `/metrics`（请求量/错误/耗时/低置信） |
| 单次决策详情 | 决策日志 JSONL 的 candidates + preference 字段 |

每次容差分流生效时，决策日志 `preference` 字段记录 `{task, model, note}`，note 含实际分差与容差，可审计每一条分流决策。
