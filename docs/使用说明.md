# 使用说明

本文面向调用路由服务的开发者和管理模型池的运营人员。生产架构和启动方法见 [部署说明](https://github.com/xwbmotor/cmtoken-auto-model-router/blob/master/docs/Ubuntu生产部署.md)。

## 接入服务

你需要服务的 Base URL 和自己的 MaaS API key。v0.14.8 已验收的生产部署使用 `passthrough`：路由器用调用方的 key 请求上游，租户权限、配额和计费由上游执行。管理端的 `ADMIN_TOKEN` 不能当业务 key 使用。

| 配置 | 示例 |
|---|---|
| Base URL | `https://<服务域名>/v1` |
| API Key | 调用方的 MaaS key |
| Model | `cmtoken-auto` |

模型名可以由管理员修改，查询 `/v1/models` 可确认当前入口。生产配置使用 `cmtoken-auto` 时，`auto` 不再是路由别名。允许点名模型时，也可传已注册且有权限的具体模型 ID；点名仍受能力和容量检查约束。

### Python

以下示例使用 OpenAI Python SDK。先在调用环境中设置 `ROUTER_BASE_URL` 和 `MAAS_KEY`；示例会发起真实模型调用。

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url=os.environ["ROUTER_BASE_URL"],
    api_key=os.environ["MAAS_KEY"],
)
response = client.chat.completions.create(
    model="cmtoken-auto",
    messages=[{"role": "user", "content": "用一句话解释快速排序"}],
)
print(response.choices[0].message.content)
```

流式输出将 `stream=True` 传给 `create`，逐段读取 `chunk.choices[0].delta.content`。工具调用或推理输出未必放在 `content` 中，应用应按自己使用的上游协议处理。

### curl

```bash
curl "$ROUTER_BASE_URL/chat/completions" \
  -H "Authorization: Bearer $MAAS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"cmtoken-auto","stream":true,"messages":[{"role":"user","content":"你好"}]}'
```

SSE 请求应持续读取到结束，不要只收到第一个片段就判定成功。排障时同时检查 HTTP 状态、正文和结束标记；200 只说明 HTTP 层成功，不能证明回答质量。

## 路由怎样选择模型

服务先检查启用状态、权限、工具等能力要求及上下文容量，再根据任务类型和难度比较合格候选。评分使用配置中的质量、用户成本、平台资源成本、时延和健康信息。相同问题在模型池、配置或负载变化后可能得到不同选择。

语义复核用于检查任务分类。`shadow` 只记录建议，`active` 才可能采纳；采纳还受置信度、灰度和失败处理策略约束。Judge 则在回答后抽样评分，两者用途不同。详细规则见 [路由设计](https://github.com/xwbmotor/cmtoken-auto-model-router/blob/master/docs/路由设计说明.md)。

需要保持同一会话的模型倾向时，可在请求头中传入稳定的 `x-session-id`。会话绑定调用方与上游，只在候选仍合格时生效。当前 Go 会话状态在进程内保存，重启后不保留；会话黏性也不代表服务替你保存聊天上下文，历史消息仍须随请求发送。

## 管理模型和策略

打开服务首页，用管理员凭证登录。日常操作按页面的“查看 → 编辑草稿 → 查看影响 → 发布”进行。

- 新模型可以从上游发现或手工登记。先确认模型归属、价格、能力和上下文，再做连接检查、体检或评测，最后启用并发布。发现成功不代表已经可以参与路由。
- 策略预览用于比较配置变化对固定样例的影响，不能当作真实业务收益。调整后先检查被排除的候选及原因，再看评分变化。
- 发布前确认模型连接、分类与评审设置中的凭证是否齐全。配置过期时会拒绝覆盖，刷新后重新核对草稿。
- 体检和稳定性巡检主要检查可用性；交错评测用于同一时间窗口的模型比较。只有带完整输入和有效评审的结果才能支持质量判断，结果不会自动替代线上评分。

## 看懂日志和指标

| 记录 | 用来回答什么问题 |
|---|---|
| 决策日志 `decisions-*.jsonl` | 为什么选这个模型，尝试过谁，最终是否交付，耗时与费用是多少 |
| 语义复核 `semantic-reviews-*.jsonl` | 分类复核是否完成，与初始判断是否一致 |
| Judge 记录 `judge-reviews-*.jsonl` | 哪些回答被抽样，评审是否成功，评分依据是什么 |
| 容器日志 | 启动、连接、配置发布或停止时发生了什么运行错误 |

优先用请求 ID 关联记录，不要只比较总条数：一次业务请求可能有多次上游尝试，也可能稍后才收到后台评审。没有抽样记录不一定是故障，需先看开关、采样比例、预算和完成状态。

TTFT 表示首段正文到达的时延；首个思考或工具输出、响应头、完整响应另有统计。P95 需要足够的同口径样本，不能把少量体检、模拟上游或不同模型的数字混作生产承诺。参见 [时延说明](https://github.com/xwbmotor/cmtoken-auto-model-router/blob/master/docs/latency-observability.md)。

## 数据留存

请求原文是否记录由 `decisionLog.redactMessages` 控制，回答正文由 `decisionLog.logAnswerText` 控制。仓库配置默认隐藏请求原文且不记录回答正文，但实际部署可以修改，导出前必须核对当前设置和样本内容。

即使隐藏了消息原文，错误详情、模型输出或其他字段仍可能包含敏感信息。不要直接分享整个 `data/` 或 `.env`；按用途导出必要记录，检查凭证、个人信息及业务内容。留存与磁盘清理说明见 [运行证据](https://github.com/xwbmotor/cmtoken-auto-model-router/blob/master/docs/operations-evidence.md)。

## 常见问题

| 现象 | 先检查 |
|---|---|
| 400 或模型不存在 | 是否还在用旧入口 `auto`；具体模型是否注册；请求字段和容量是否有效 |
| 401 / 403 | 是否误用了管理 key；调用方 key 是否有效、是否有模型权限 |
| 429 | 上游租户额度及当前并发；不要通过连续换模型绕过限制 |
| SSE 卡住或缺少结尾 | 客户端是否持续读取、反代是否缓存、上游是否超时或断开 |
| 没有质量评分 | Judge 是否启用、是否被抽样、评审连接与额度是否正常 |
| 修改没有生效 | 草稿是否发布成功，是否存在配置冲突，Go 配置状态是否就绪 |

提交故障信息时提供时间、请求 ID、状态码及脱敏后的错误。重启或回滚前先阅读部署说明，Go 后台结果需要 Node 在排空期间继续接收。
