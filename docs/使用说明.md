# Auto Model Router 使用说明

> `model` 填 `auto`，剩下的交给路由器：每笔请求按任务类型与难度，从模型池里自动挑最合适的一个。简单问题走便宜模型省钱，难问题走强模型保质量，失败自动换下一个。
>
> OpenAI 兼容协议——现有代码改两处（`base_url` 和 `model`）即接入，流式、工具调用、JSON 模式原样透传。

本文按「接入 → 理解 → 控制 → 观测 → 排障」推进，面向应用开发、测试与运营三类角色。

## 1. 五分钟接入

### 你需要两样东西

| 你需要 | 哪里来 |
|---|---|
| API Key（`ROUTER_ACCESS_KEY`，或 passthrough 模式下用你的 MaaS key） | 找运维申请 |
| Base URL | `http://<服务地址>:8787/v1` |

### Python（OpenAI SDK）

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8787/v1",      # ← 原来是 MaaS 地址
    api_key=os.environ["ROUTER_ACCESS_KEY"],
)

resp = client.chat.completions.create(
    model="auto",                             # ← 原来是具体模型名
    messages=[{"role": "user", "content": "用一句话解释什么是快速排序"}],
)
print(resp.choices[0].message.content)
print("实际使用的模型:", resp.model)           # 响应里带本次选中的模型
```

### Node.js（openai npm 包同理）

```javascript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://127.0.0.1:8787/v1",
  apiKey: process.env.ROUTER_ACCESS_KEY,
});

const resp = await client.chat.completions.create({
  model: "auto",
  messages: [{ role: "user", content: "分析这段 Java 代码的并发安全问题" }],
});
console.log(resp.choices[0].message.content);
console.log("实际使用的模型:", resp.model);
```

### curl

```bash
curl http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $ROUTER_ACCESS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"用一句话解释什么是快速排序"}]}'
```

任何 OpenAI 兼容客户端适用同一替换规律：**改 `base_url`，`model` 用 `auto`**。`model` 不传也视为 auto。

### 真实响应长这样

```json
{
  "choices": [
    {
      "finish_reason": "stop",
      "message": {
        "content": "快速排序是一种分治算法：选一个基准值把数组分成两部分…",
        "role": "assistant"
      }
    }
  ],
  "model": "deepseekv4-flash",
  "usage": { "prompt_tokens": 15, "completion_tokens": 40, "total_tokens": 55 }
}
```

`model` 字段告诉你这笔请求实际用了谁。上面这个问题被识别为通用问答，路由给了低成本模型；同一句换成「分析 Java 并发安全问题」，`model` 会变成更强的代码模型——这就是 auto 在干活。

## 2. auto 是怎么工作的

每一笔 `model=auto` 的请求经过五步：

1. **识别任务**（<1ms）：按文本特征把请求归入 6 大类（通用问答 / 代码 / 分析推理 / 内容创作 / 数据结构化 / 智能体）之一，再细分到约 30 个小类（如 调试、代码评审、SQL、前端、数据抽取、翻译、多步规划、Web 搜索…），并估算 0~1 的难度。带工具调用、图片、要求 JSON 输出的请求难度上调。
2. **低置信复核**（可选，约 20ms）：规则分类把握不足（置信度低——置信度是证据强度的函数：任务关键词全部被否定包裹如「不要写代码」、概念问答「什么是 X」、引用性提及「总结这段代码」会下调；而「禁止递归，写循环版本」这类有肯定命中的明确请求不下调）的请求，再让复核模型独立判一遍任务类型。三层文本口径统一：分类只看 user 消息（最后一条为主 + 最近 2 条上下文），system 提示与 assistant 历史不进分类。复核者管理后台可选：自训练小模型（本网部署、毫秒级）、MaaS 大模型、或**级联**（小模型先判，小模型失败或拿不准时升级大模型兜底——大部分请求只花小模型的成本，分不准的少数才付大模型调用）。复核可配为「仅观察」（只记录分歧不改路由）或「正式采用」（按复核结果路由）。
3. **过滤候选**：剔除被禁用的、租户无权调用的、熔断中的、上下文窗口不够的模型；再按当前成本档位划出价格带，带外的（太贵**和太便宜**）都出局。
4. **评分排序**：`score = 质量分 − 成本敏感×用户成本指数 − 算力敏感×算力消耗指数 − 时延敏感×时延 − 不确定性惩罚 + 自建奖励 + 市场信号微调`。质量分来自标准评测集实测，市场信号来自真实流量的决策日志聚合——静态跑分是先验，真实使用是后验，两者互补。质量不过线的候选降级为后备。成本是双指标：用户成本指数按算力豆结算价归一（用户侧，每豆换多少 token），算力消耗指数按自建部署资源强度（设备×卡×卡价÷吞吐，平台侧）；两者独立权重、可背离，路由同时照顾用户省豆与平台省卡。
   - **相对质量损失上限（v0.5.1）**：加权求和可能让成本项淹没质量差距（复杂代码任务低质量模型凭便宜胜出）。评分前先按难度分档过滤：候选质量低于本场最优 `relQualityCap.simple 0.08 / balanced 0.04 / complex 0.02` 以内的才允许胜出。全部超限时退回绝对质量地板，仍无候选则全量兜底（保可用性）。**v0.5.2：任务偏好（taskPreferences）不可绕过此闸门**——偏好目标必须在 qualified 池内且分差 ≥ 0，超限模型只能作兜底不能被偏好提升到首位（Codex 二审：原实现负分差天然过容差，低质量模型可被定向点名选中）。
   - **小类分数平滑（v0.5.1，v0.5.2 保守化）**：质量分对 30 个小类按 `小类实测 × n/(n+k) + 大类分 × k/(n+k)` 平滑（k=`routing.subtaskSmoothK`，默认 8→**32**）。v0.5.2 新增两道闸：`subtaskMinSamples`（默认 4，样本不足直接用大类分）与 `subtaskMaxAdjust`（默认 0.06，小类对大类分修正幅度封顶）——修 Codex 二审指出的「n=5 小类权重 38.5% 过激进，debugging 0.580(n=5) 把 0.955 拉到 0.811」。
5. **转发与兜底**：会话粘住同一模型保证多轮风格一致；选中的模型调用失败，按评分顺序自动换下一个重试（最多 3 次），熔断器隔离持续故障的模型。分类或评分环节即使出错，请求也不会因此失败。
   - **能力声明 fail-closed（v0.5.1）**：请求带 tools / response_format=json / 图片输入时，只有显式声明 `capabilities.tools / capabilities.json / capabilities.vision = true` 的模型进入候选，未声明视为不支持——宁可拒绝也不错发（chat / stream 历史配置普遍未显式声明，豁免）。当前 caps（tools=true/json=true，vision 仅 Qwen3.8-27B=true）经 2026-08-24 真实 MaaS 探测证实：三模型 tools 均返回合法 tool_calls；json_object 均出合法 JSON（Qwen3.8 需 max_tokens≥500，思考消耗 token 多）；json_schema 均不支持（返回自由文本，路由只判 json_object 不受影响）。vision 已实测闭环：带图请求自动收敛到唯一 vision 模型 Qwen3.8-27B（识别测试图三色正确，86/10 tokens）；注意 Qwen3.8 为思考型模型，`minimumCompletionTokensForReliableAnswer=16384`，客户端显式传小 `max_tokens`（如 500）会触发 `completion_budget_too_low` 拒绝——带图请求建议不传 max_tokens 或传 ≥16384。

```
请求(model=auto)
   │
   ▼
①识别任务 ──规则分类──▶ 6 大类 → 30 小类 + 难度 0~1        [<1ms]
   │ 置信度低?
   ├──────────────▶ ②低置信复核（小模型为主，拿不准升大模型） [≈20ms, 可仅观察]
   ▼
③过滤候选 ──禁用/权限/熔断/上下文/成本档位价格带──▶ 合格模型
   ▼
④评分排序 ──质量 × 成本 × 时延 加权──▶ 最优 + 后备序列
   ▼
⑤转发与兜底 ──会话粘性→失败自动换下一个→决策写响应头──▶ 调用方
```

**分类体系**（与业界任务口径对齐）：4 大类 30 小类——⚙️代码（生成/调试/评审/SQL/前端/DevOps/Shell/文件/仓库 9 小类）、🤖智能体（多步规划/Web 搜索/工作流执行等 6 小类）、📋数据（抽取/转换/打标/摘要/翻译/数学 6 小类）、💬写作与对话（文案/角色扮演/客服/研报等 9 小类）；另有 📌点名模型 单列。分类只影响展示与统计口径，真正决定路由的是第 ④ 步的实测能力分。

**实测示例**（同一服务、三种请求）：

| 请求 | 识别任务 | 选中模型 |
|---|---|---|
| 「用一句话解释什么是快速排序」 | 通用问答 | deepseekv4-flash（低成本） |
| 「分析这段 Java 代码的并发安全问题」 | 代码 | Qwen3.8-27B（代码强） |
| 「从文本提取姓名电话城市返回 JSON」 | 数据抽取 | qwen36-35b（抽取定向分流） |

显式指定模型名（如 `model="Qwen3.8-27B"`）不走以上流程，直接透传——便于兼容旧业务、做模型对照。指定的模型不存在或未启用时返回 `400 模型不存在或未启用: <名字>`。

## 3. 会话粘性

与固定模型不同，auto 理论上每轮可以换模型。多轮对话里这会导致风格跳变，所以路由器会记会话：

- 请求带 `x-session-id` 头（或复用已有值），路由器记住该会话上次落在哪个模型；
- 后续请求在**任务类型与难度同型、且旧模型评分仍接近最优**（分差 ≤ `sessionStickinessMaxGap`，默认 0.05）时继续用它——v0.5.4 起粘性加了闸：先问简单题再问复杂题（难度升档）、或旧模型明显劣化时，粘性自动让位、按新请求重新路由，不再把整个会话钉死在第一个模型上；
- 旧模型被能力过滤出局（比如突然要求看图）时自然换人；
- 粘性默认 30 分钟过期，之后按新请求重新路由。

```
x-session-id: my-conversation-123
```

**实测**：同一 `x-session-id` 先问代码题（选中 Qwen3.8-27B），下一轮发闲聊，仍由 Qwen3.8-27B 回答——对话人格保持一致。

## 4. 控制路由范围

### 显式点名（最直接）

`model` 填具体模型名即直连该模型，跳过路由。管理端可配置 `defaultExplicitModel` 与是否允许显式指定。

### 成本档位（Cost Tier）

管理端「业务策略」tab 有四档预设，语义是**价格带**而不是价格上限：

| 档位 | 价格带（costIndex） | 适合 |
|---|---|---|
| 省钱 budget | 0 ~ 0.2 | 批量跑量、对质量不敏感 |
| 均衡 balanced | 0 ~ 0.5 | 日常默认 |
| 质量 quality | 0.15 ~ 1 | 对外交付、复杂任务 |
| 顶配 max | 0.2 ~ 1 | 质量优先不计成本 |

高档位同样排除过于便宜的模型（防止低端拉低质量），低档位排除超出预算带的模型。档位是全服务级配置（管理端调，不走请求参数）；调档后先用「调整影响预估」预览多少任务会换模型再发布。

### 路由风格预设（四权重一键组合）

价格带之上，「业务策略」tab 另有一组**路由风格**预设——质量/用户成本/算力消耗/时延四个评分权重的一键组合，与成本档位正交：

| 风格 | 用户成本权重 | 算力消耗权重 | 时延权重 | 质量底线 | 适合 |
|---|---|---|---|---|---|
| 质量优先 | 0.08 | 0.05 | 0.08 | 0.80 | 对外交付、演示评测 |
| 用户成本优先 | 0.45 | 0.10 | 0.10 | 0.72 | 替调用方省豆 |
| 运营成本优先 | 0.22 | **0.40** | 0.10 | 0.72 | 平台省卡——流量导向低占用高并发模型（如 qwen3.6） |
| 效率优先 | 0.15 | 0.05 | **0.45** | 0.72 | 交互场景、首字快 |
| 均衡风格 | 0.22 | 0.10 | 0.14 | 0.72 | 现网默认组合 |

选任一风格后四个滑条和质量底线联动到位，标记为「自定义」档；后续手动微调任一滑条即脱离预设。同样先看「调整影响预估」再安全发布。

### 想看某类任务都路由给了谁

管理端「效果洞察 → 任务榜单」按任务类型聚合近期决策：每类任务的首选模型、份额、失败率——流量花在了哪、谁在扛，一眼可查。

## 5. 观测：每笔请求的透明度

### 响应头（每笔都有）

| 响应头 | 含义 |
|---|---|
| `x-request-id` | 本次请求 ID（可回查决策日志；客户端也可自带） |
| `x-router-selected-model` | 实际调用的模型 |
| `x-router-suggested-model` | auto 评分建议的模型（灰度未采用时与 selected 不同） |
| `x-router-task` | 识别出的任务大类 |
| `x-router-route-method` | 判断方式（rules / semantic） |
| `x-router-reasoning-level` | 推荐的思考深度（off / standard / high） |
| `x-router-cost-tier` | 当前成本档位 |
| `x-router-shadow` | 本请求是否未真正采用 auto 建议（灰度期观察流量） |

想精确复盘「为什么我的请求分给了模型 X」：拿 `x-request-id` 对应决策日志（`data/decisions/`，含全部候选评分明细），或在管理端「调试工具」粘贴原文重放——显示任务类型、难度信号、每个候选的得分与 fallback 顺序，预演零成本。

流式请求的成功判定在**流尾**而非首包（v0.5.1）：SSE 中断只记失败不双记，TTFT（首 token 时延）单独统计。非流式成功记在**客户端交付完成后**（v0.5.3）：响应写回且 socket 正常关闭才记成功，客户端中途断开记失败不记假成功。预算采用**预占-结算**（v0.5.1 起，v0.5.2 修复结算数学、v0.5.3 修复压力口径）：请求开始按估算预占，结束按上游返回的实际 usage 冲正；无 usage 的请求保留估算值（结算后同样冲减预占）。台账三口径分解：`estimatedSpendYuan`（未结算预占余额）/ `settledActualSpendYuan`（按真实 usage 结算累计，对账口径）/ `settledEstimatedSpendYuan`（无 usage 保留估算结清累计）——预占 10 实际 15 记 15（v0.5.1 会错记 5，已修）。预算压力 =（已结算实际 + 已结算估算 + 在途预占）/ 每日预算（v0.5.3 修复：原只看在途预占，结算后压力归零，预算耗尽永不触发降级）。`/metrics` 里 `router_ttft_ms_count/sum`（首包时延）、`router_stream_total{outcome}`（流式完成/中断）、`router_budget_settled_yuan`（当日已结算消费，预算关闭也持续记账）、`router_budget_pending_reserves`（在途预占数）、`router_budget_settled_beans`（已结算算力豆）可直接观测（v0.5.4 起全部真实输出，此前部分指标名未实现）；生产环境（非本机绑定）`METRICS_TOKEN` 强制，未配置启动即拒绝。

### 多调用方归因（key 指纹）

多个业务方共用路由器时，每笔决策日志记一个 **key 指纹**（调用方 API key 的 sha256 前 8 位十六进制，不存明文）。管理端「最近请求」可按指纹下拉筛选，只看某一个调用方的流量；`GET /admin/api/decisions?key=<指纹>` 按指纹导出。审计口径：日志能回答「这个业务方用了多少、选了什么模型」，但反查不出原始 key。

「最近请求」列表默认不显示指纹（鼠标悬停灰色小字可见）；上方下拉「全部调用方 / 某指纹」选中后才按调用方过滤。

### 「不做 auto 会怎样」对比（v0.5.0）

业务策略页「调整影响预估」下方新增对比表：把同一批代表任务**全部固定给某一个模型**（即不做 auto 的情形）与当前策略并排比较——质量均值、用户成本指数、算力消耗指数、时延指数，各带相对当前策略的百分比变化（绿=更优）。用途有二：

- **换策略前**：看清这套策略相对「直接用某个模型」到底省多少豆、质量让多少；
- **横向汇报**：和固定单模型的方案比较，auto 的收益不再靠感觉，一行一个百分比。

表内每行还能看到该模型是否满足全部代表任务的能力要求（不满足会标注，说明它单扛不住全部流量）。

### 三层分类架构（v0.5.0）

「质量复核」页改为三层漏斗布局，每层独立卡片、独立配置：

| 层 | 组件 | 作用 | 配置 |
|---|---|---|---|
| L1 规则层 | 内置规则（代码实现） | 关键词+正则分类，零成本毫秒级，所有请求的第一道判定 | 规则内置于 `src/router.mjs`（4 大类 30 小类口径），页面不可改；调优走组件体检验证后发版 |
| L2 小模型复核层 | 自训练小模型（本网 HTTP 端点） | 规则置信度不足时介入 | 端点地址 + 启用开关；在使用手册「小模型部署」节 |
| L3 大模型复核层 | MaaS 大模型 | 小模型也拿不准时兜底（或直接用大模型复核） | 选哪个大模型（下拉）+ 级联阈值 |

页面同时显示「规则高置信定案占比」——最近真实流量里 L1 直接定案（无需复核）的比例，越高说明规则层消化得越多、复核成本越低。全局开关「由谁复核」决定 L2/L3 哪几层参与，级联方式下大部分请求只付 L2 成本、少数才升级 L3。

### 模型能力数据：Excel 导入导出（v0.5.0）

模型管理页的能力档案支持 Excel 模板：**下载导入模板（Excel）**得到一个 CSV 文件（Excel 双击直接打开，中文不乱码），每行一个模型、各列为官方榜单分（gpqa_diamond / swe_bench / livecodebench）与评测门限分（evalGate 七列）；在 Excel 里改完保存，**上传导入（.csv / .json）** 选它上传即生效。仍兼容原 JSON 格式（subtasks 等深层字段用 JSON 导）。导入语义与之前一致：留空保留现值。

### 推理档位的两种显示

「最近请求」里的推理档位（off / standard / high）是路由器按请求复杂度给出的**建议值**。仅当所选模型的思考参数已实测验证（管理端显示「已验证」）时才真正下发上游；未验证模型显示为「推理 high（建议未生效）」——上游按自身默认行为执行，档位仅供参考。

### 计费口径

路由器不加价：付的就是选中模型的标准价。passthrough 模式（MaaS 分流部署）下用的还是你自己的 key，账单落你的租户，与直连完全一致；管理端的成本面板是估算交叉核对用，正式计费以 MaaS 账单为准。

## 8. 排障

| 现象 | 处置 |
|---|---|
| 后台「连接失败」 | 填的是 `ADMIN_TOKEN` 而非 `ROUTER_ACCESS_KEY`；改 `.env` 后要重启 |
| API 401 | 客户端用 `ROUTER_ACCESS_KEY`，格式 `Authorization: Bearer ***`；passthrough 模式用 MaaS key |
| 改参数没生效 | 必须点「安全发布」；浏览器 `Ctrl+F5`；灰度期部分流量仍走对照模型（看 `x-router-shadow`） |
| 400 模型不存在或未启用 | 显式点名的模型名不对（大小写敏感）或未启用，`GET /v1/models` 一查便知 |
| 预算一直显示 0 | 预算未启用 / 每日预算为 0 / 启用模型缺单价 |
| 语义复核没触发 | 高置信度请求不复核；置信度低于阈值且文本够长才触发 |
| 语义复核已开 active 但部分请求仍走规则层 | 语义有独立灰度比例（管理页「语义灰度比例」，默认 5%）；未放量桶的请求记 `rollout_hold`、后台仍照常分类观察，属正常对照组。分桶按会话（`x-session-id`）稳定——同会话重试不会一会儿规则层一会儿语义层 |
| 400 请求体不是合法 JSON | 客户端以 `Content-Encoding: gzip/deflate/br` 压缩请求体时（v0.8.1 起支持，自动解压）；若仍报此错，确认路由器版本 ≥0.8.1，或先在客户端关闭请求体压缩。报「解压失败」=压缩数据损坏；报「解压后请求体超过上限」=解压后超 50MB（防压缩炸弹）。**注意 error.type**：v0.8.4 起解析层错误按真实类型区分——`invalid_request_error`=JSON 损坏/走私请求（部分代理会把 absolute-form 重复请求拼进连接），`unsupported_content_encoding` 仅用于 415 编码不支持 |
| 415 不支持的 Content-Encoding | 请求体用了路由器不支持的压缩编码（如 zstd）——用 gzip/deflate/br，或在客户端关闭请求体压缩 |
| 服务起不来 EADDRINUSE | 已有实例在跑：先 `curl /health` 确认，不要盲目重启 |

`GET /health` 返回服务与上游连通性；`upstreamConfigured: false` 说明 `.env` 缺 `MAAS_API_KEY` 或启动目录不对。

## 9. 上线流程（推荐）

1. 主路由与语义复核都设为 Shadow（仅观察）。
2. `npm run benchmark`（先 `--dry-run` 看题）校准质量/成本/时延指数。
3. 收集 200~500 条真实任务，重点看复杂任务是否被低估难度。
4. 主路由改 Active，生效流量 5%~10% 起步。
5. 观察错误率、fallback、自建承载率，逐步放大 25%→50%→100%，每步先做影响模拟。
6. 稳定后再评估开启语义复核 Active（v0.7.0 起从「语义灰度比例」5% 起步放量，观察 `router_semantic_total{stage="rollout_hold"}` 对照组与放量桶的差异，逐档放大）、每日预算保护、思考深度自动调节。

## 10. 边界

- 仅支持 `messages` 格式（不支持裸 `prompt`）；流式、工具调用、JSON 模式全兼容。
- 请求体压缩（`Content-Encoding: gzip/deflate/br`，含复合编码）自动解压后处理（v0.8.1）；解压后大小同样受路径级上限约束（聊天 50MB）。不支持 zstd 等其余编码（415）。
- 请求/健康指标在内存，重启清空（决策日志与预算账本落盘）。
- 预算是估算值，正式计费以 MaaS 实际 usage 为准。
- 模型质量分需随模型演进用真实业务样本校准（eval gate，见运营手册 SOP）。
- 对外网开放前需补 TLS、网关访问控制、限流、租户隔离与持久化监控（参考 `docs/反代集成.md`）。


## v0.7.2 八审运维补丁：SEMANTIC_BUCKET_SECRET（生产切 active 必填）

v0.7.1 起语义灰度按 HMAC(secret) 分桶；v0.7.2 起生产 compose 强制要求该变量，否则 active 模式启动即报错。shadow 模式可缺省。

```bash
# 生成 32 字节随机 secret（任选其一）
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
openssl rand -base64 32
```

写入宿主机 .env 后 compose 自动注入容器：

```
SEMANTIC_BUCKET_SECRET=<粘贴上面生成的字符串>
```



## v0.7.3 九审计量修正

- **secret 强度**：active 模式要求 `SEMANTIC_BUCKET_SECRET` ≥32 字节（约 43 位 urlsafe 字符）。过短启动即报错，按报错里的命令重新生成即可。
- **隐私**：决策/复核日志中的灰度分桶键已改为 HMAC 短指纹（形如 `sid:9f3ab07c2d1e`），你的会话 ID 不会原文落盘。
- **reload 保护**：管理页或 API 触发的配置 reload 与重启一样校验 secret——磁盘配置被改成 active 而 secret 缺失/过短时 reload 会拒绝，不会绕过保护。
**为什么必要**：进程级随机 secret 每次容器重启会重新洗牌——同一个租户重启前是实验组，重启后可能进对照组，5%→25% 灰度期间成本与质量对比会被交叉污染。


## v0.7.4 十审（隐私与发布证据）

- **会话标识脱敏**：决策与复核日志中的会话标识是 HMAC 指纹（形如 `sidfp:9f3ab07c2d1e4f5a`），你传入的 `x-session-id` 原文不会写进任何日志。同一会话的指纹恒定，跨日志可对账。
- **发布报告**：`npm run test:release` 生成的报告带 `validForRelease` 标记——只有「干净工作区+恰好打了版本 tag」时为 true。报告作为发布证据归档，不回填进源码 tag。
- **secret 口径**：`SEMANTIC_BUCKET_SECRET` 的 32 字节要求是长度下限；请始终用文档给的随机生成命令产出。

## v0.8.0 Judge（异步质量评审）

- **是什么**：对已成功完成的请求按固定比例抽样，事后异步调用评审模型（默认 glm-5.3）给回答打分。**只做离线观察，绝不进在线路由决策闭环、不增加用户时延、评审失败不影响正常回答。**
- **评分口径**：四维拆分（正确性 / 指令遵循 / 完整性 / 安全性），无参考答案可验证的维度标「不可验证」（verifiable=false，不计分）；分类核对（task 大类是否判对）是独立事件，与质量分不混总分。
- **抽样**：按 requestId 的 HMAC 稳定分桶（与语义灰度同 secret、不同域前缀），同一请求重放结果恒定，客户端无法操纵；建议 1~5% 起步。
- **护栏**（四重，超限当日停评并落 skipped 事件）：每日调用上限 / 每日 token 上限 / 单次超时（默认 60s，超时强断）/ 连续失败熔断（默认 5 次，冷却后半开试探）。
- **数据面**：独立事件流 `data/decisions/judge-reviews-*.jsonl`（与决策/语义复核日志隔离）；事件含 judgeModel、rubric 版本与 hash、answeredModel、task/tier、sessionFingerprint（HMAC 指纹，原文不落）、usage、时延。
- **管理页**：「Judge · 异步质量评审」卡片——开关/抽样率/评审模型/双预算/超时/熔断阈值/分类核对开关/今日用量。默认关闭。
- **上线建议**：先开 1% 抽样 shadow 观察一周；评审结果达样本量（≥500 条分层样本）+人工抽检一致率达标后，再谈是否用于策略模拟/模型质量分（那是 v0.9+ 的事）。

## v0.8.3 Judge 十二审收口（5×P1 + 4×P2）

- **评分输入修复**：v0.8.0 给评审模型的是完整响应信封/原始 SSE 字节（usage、chunk JSON、`data:`/`[DONE]` 行全部混进评分输入）。v0.8.1 两条交付路径都提取**纯正文**：非流式解析 `choices[0].message.content`，流式增量收集 `delta.content`（64KB 软上限，多字节 UTF-8 字节边界安全；undici chunk 是 Uint8Array 需 Buffer 化的坑已修并有单测）。
- **预算预占-结算制**：v0.8.0 的 `canCall()` 只读不占，并发在途可全部穿透双预算闸。v0.8.1 改 reserve→settle：发起即预占调用名额+预估 token，完成按实际 token 冲正、失败退回；半开状态只放一个探针调用。状态持久化 `data/judge-guard-state.json`——重启不再清零当日用量/熔断态。
- **半开探针状态机（v0.8.3 修复）**：探针预占遇预算耗尽不再卡死——预算检查先于状态迁移，探针被 release（如缺 API Key 未发起调用）时回滚 half-open→open，跨日预算归零后可正常恢复试探；`invariantOk` 不变量随 snapshot 暴露。
- **管理面双口径（v0.8.3）**：「今日用量」pill 同时展示进程计数（抽样/评分/失败，重启清零）与 Guard 持久化预算（used/max、剩余额度、熔断态，重启不重置）——预算与熔断以 Guard 为准，与执行闸一致。Prometheus 新增 `router_judge_guard_calls_today`/`router_judge_guard_tokens_today`（持久化口径 gauge）与 `router_judge_total{stage="persistErrors"}`（状态文件写盘失败计数）；`router_judge_circuit_state` 改为请求时实时取值。
- **Guard 状态原子持久化（v0.8.3）**：临时文件+rename 原子替换（进程中断不再留截断 JSON 导致预算静默重置）；`openedAt` 随状态保存，重启不重算熔断冷却期；`judge.guardStatePath` 不可热更（改路径需重启，管理 API 会显式拒绝）。
- **分类核对契约**：rubric 细类编码表（sql/debugging/write 等）与路由枚举（coding/reasoning/creative/extraction/agent/default）错位已修——taskCheck 只判大类，subTask 仅参考；显式指定模型的请求跳过核对；评审返回的 suggested_task 做枚举校验。
- **审计链独立**：judge-reviews 流启停不再依赖 `decisionLog.enabled`（judge 开+决策日志关的付费无审计漏洞已堵，配置校验双保险直接拒绝该组合）；优雅关停 flush 补 judgeLog 排空；空 verdict（`{}`）不再计成功。
- **脱敏**：`judge.redactPatterns`（正则数组）——发送评审模型前遮蔽匹配片段，事件流仍走 sessionFingerprint 指纹。
- **今日用量**：UTC 自然日翻转（此前进程级计数永不翻转）；release 门禁要求镜像 imageId+OCI revision 证据；judge-e2e 捕获子进程输出（启动失败不再 `stdio:'ignore'` 黑盒）。
