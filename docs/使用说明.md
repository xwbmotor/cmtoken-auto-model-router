# Auto Model Router 使用说明

把业务应用的 `base_url` 指向本服务、`model` 写成 `auto`，剩下的交给路由器：每笔请求按任务难度、质量、成本、时延自动挑选最合适的模型。OpenAI 兼容协议，现有代码改两行即接入。

本文面向三类人员：**应用开发**（接入调用）、**测试人员**（验证路由与 fallback）、**运营人员**（管理后台调策略）。

## 1. 五分钟接入

### 第一步：拿到两样东西

| 你需要 | 哪里来 |
|---|---|
| `ROUTER_ACCESS_KEY` | 找运维申请，调用 API 的客户端 Key |
| API Base URL | `http://<服务地址>:8787/v1` |

### 第二步：改两行代码

Python（OpenAI SDK）：

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8787/v1",      # ← 原来是 MaaS 地址
    api_key=os.environ["ROUTER_ACCESS_KEY"],
)

resp = client.chat.completions.create(
    model="auto",                             # ← 原来是具体模型名
    messages=[{"role": "user", "content": "分析这段 Java 代码的并发问题"}],
)
print(resp.choices[0].message.content)
```

curl：

```bash
curl http://127.0.0.1:8787/v1/chat/completions \
  -H "Authorization: Bearer $ROUTER_ACCESS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"auto","messages":[{"role":"user","content":"今天星期几？"}]}'
```

任何 OpenAI 兼容客户端都适用同一个替换规律：**改 `base_url`、`model` 用 `auto`**，消息结构、流式、工具调用等参数原样透传。

### 第三步：确认通了

响应头里的 `x-router-selected-model` 会告诉你这笔请求实际用了哪个模型（见第 8 节）。

## 2. 先理解三个 Key

| 配置 | 谁使用 | 用途 |
|---|---|---|
| `MAAS_API_KEY` | Auto Router 服务本身 | 调用 MaaS 上游 |
| `ROUTER_ACCESS_KEY` | 接入的业务应用 | 调用 `/v1/chat/completions` |
| `ADMIN_TOKEN` | 运营、管理员 | 登录管理后台和访问 `/admin/api/*` |
| `LITELLM_MASTER_KEY` | LiteLLM，可选 | 仅采用 LiteLLM 组合部署时使用 |

三个 Key 应当互不相同。不要把 `MAAS_API_KEY` 提供给业务客户端，也不要把任何真实 Key 写进代码、截图或文档。

## 3. auto 是怎么工作的

`model="auto"` 的每一笔请求会经过四步：

1. **任务理解**：按文本特征识别任务类型（通用/代码/推理/抽取/创意）与难度（0~1）。带工具调用、图片、要求 JSON 输出的请求难度会略加。
2. **候选过滤**：按当前成本档位（省钱/均衡/质量/顶配）划出价格带，过滤能力不达标、健康状态异常（熔断中）的模型。
3. **评分排序**：对每个候选按「质量分 − 成本敏感度×成本指数 − 速度敏感度×时延指数」综合打分，质量不过线的直接淘汰。
4. **兜底保护**：选中模型失败时按候选顺序自动 fallback；同会话（`x-session-id` 相同）30 分钟内尽量粘住同一模型，避免多轮对话风格跳变。

显式指定模型名（如 `model="qwen36-35b"`）则不走以上流程，直接透传——便于兼容旧业务和做模型对照。

## 4. 管理后台怎么用

浏览器打开 `http://<服务地址>:8787/`，右上角填 `ADMIN_TOKEN` 点「连接」。页面按 tab 组织：

| Tab | 干什么 | 谁用 |
|---|---|---|
| 总览 | 请求量、auto 占比、错误率等核心指标 + 当前策略快照 | 所有人 |
| 业务策略 | 成本档位、滑条参数、影响预估、安全发布 | 运营 |
| 模型管理 | 跑分校准、模型上下架、成本定价 | 算法/运维 |
| 效果洞察 | 路由体检（auto vs 单模型基线）、任务榜单 | 运营/汇报 |
| 质量复核 | 语义复核组件配置与体检 | 算法 |
| 调试工具 | 单题路由解释（这题为什么选这个模型） | 开发/测试 |
| 使用手册 | 本文档 | 所有人 |

「简单模式」只保留日常运营需要的 tab，「专家模式」开放全部参数。右上角可切换。

## 5. 业务策略怎么调

调策略的安全节奏是**先看影响、再发布**：

1. 在「业务策略」tab 选择成本档位（省钱/均衡/质量/顶配），或手动微调滑条（自动变成「自定义」）。
2. 下方「调整影响预估」会实时显示：多少任务的模型会切换、质量/成本/时延怎么变。模拟口径，不调模型、零费用。
3. 确认合理后点「安全发布」。发布前自动存档上一版到 `config/history/`，随时可回滚。
4. 高影响调整会弹二次确认——建议先把「Auto 生效流量」设为 5%~10% 观察后再放量。

主要参数速查：

| 参数 | 含义 |
|---|---|
| 成本档位 | 省钱/均衡/质量/顶配四档预设，按价格带双向过滤候选模型 |
| 最低质量目标 | 低于该质量分的候选不优先选择 |
| 成本/速度敏感度 | 越高越偏向便宜/低时延模型 |
| Auto 生效流量 | 只有该百分比的请求真正采用 auto 建议，其余走对照 |
| 运行状态 | 「正式生效」或「仅观察」（Shadow 对照） |

## 6. 服务怎么启动

需要 Node.js 20+。

```powershell
cd <项目目录>
Copy-Item .env.example .env   # 首次：复制模板并填写
notepad .env
npm test                      # 自检
npm start                     # 启动
```

`.env` 至少填写：`MAAS_API_KEY`、`MAAS_BASE_URL`、`ROUTER_ACCESS_KEY`、`ADMIN_TOKEN`、`HOST=127.0.0.1`、`PORT=8787`。

启动成功显示 `Auto Model Router listening on http://127.0.0.1:8787`。

端口被占用（`EADDRINUSE`）说明服务已在跑：先访问 `/health` 确认，确需重启时先 `netstat -ano` 找到 PID 再停止，不要盲目重复启动。

Docker 方式：

```powershell
docker compose up --build -d          # 直连 MaaS
docker compose -f compose.litellm.yaml up --build -d   # 需要 LiteLLM 时
```

容器只发布到宿主机 `127.0.0.1:8787`；`config/` 与 `data/` 已挂载，重建容器不丢配置和预算账本。

## 7. 观测与排障

### 怎么知道这笔请求选了谁

每个响应都带路由响应头：

| 响应头 | 含义 |
|---|---|
| `x-router-selected-model` | 实际调用的模型 |
| `x-router-suggested-model` | auto 评分建议的模型 |
| `x-router-task` | 识别出的任务类型 |
| `x-router-route-method` | 判断方式（rules / semantic 等） |
| `x-router-reasoning-level` | 推荐思考深度（off/standard/high） |
| `x-router-shadow` | 该请求是否未真正采用 auto 建议 |

### 这题为什么选这个模型

「调试工具」tab 输入问题，点「计算选择」：显示任务类型、难度构成信号、每个候选的评分、fallback 顺序。预演不调最终回答模型，零成本。

### 健康检查

`GET /health` 返回服务与上游连通性；`upstreamConfigured: false` 说明 `.env` 缺 `MAAS_API_KEY` 或启动目录不对。

### 常见问题

| 现象 | 处置 |
|---|---|
| 后台「连接失败」 | 确认填的是 `ADMIN_TOKEN` 而非 `ROUTER_ACCESS_KEY`；改 `.env` 后要重启服务 |
| API 401 | 客户端应使用 `ROUTER_ACCESS_KEY`，格式 `Authorization: Bearer ***` |
| 改参数没生效 | 必须点「安全发布」；浏览器 `Ctrl+F5`；Shadow 模式下实际模型仍是对照模型 |
| 预算一直显示 0 | 检查预算是否启用、每日预算是否大于 0、启用模型是否都填了单价 |
| 语义复核没触发 | 高置信度请求不复核；只有置信度低于阈值且文本够长才触发 |

## 8. 上线流程（推荐）

1. 主路由与语义复核都设为 Shadow（仅观察）。
2. 跑基准测试校准质量/成本/时延指数：`npm run benchmark`（先 `--dry-run` 看题）。
3. 收集至少 200~500 条实际任务，重点看复杂任务是否被低估难度。
4. 主路由改 Active，生效流量 5%~10% 起步。
5. 观察错误率、fallback、自建承载率与业务反馈，逐步放大到 25%→50%→100%，每步先做影响模拟。
6. 稳定后再评估开启语义复核 Active、每日预算保护、思考深度自动调节。

## 9. 当前的边界

- 请求/健康指标保存在内存，服务重启清空（决策日志与预算账本落盘）。
- 预算是估算值不是账单，正式计费以 MaaS 实际 usage 为准。
- 模型质量分需持续用真实业务样本校准（eval gate）。
- 对外网开放前需补 TLS、网关访问控制、限流、租户隔离与持久化监控。
