# Auto Model Router 使用说明

本文面向三类人员：

- 应用开发：把原来的 OpenAI/MaaS 调用地址改成 Auto Router。
- 测试人员：验证路由结果、真实模型响应和 fallback。
- 运营人员：在管理后台调整策略、灰度流量和模型参数。

## 1. 先理解三个 Key

| 配置 | 谁使用 | 用途 |
|---|---|---|
| `MAAS_API_KEY` | Auto Router 服务 | 调用中国移动 MaaS 上游 |
| `ROUTER_ACCESS_KEY` | 接入 Auto Router 的业务应用 | 调用 `/v1/chat/completions` |
| `ADMIN_TOKEN` | 运营、管理员 | 登录管理后台和访问 `/admin/api/*` |
| `LITELLM_MASTER_KEY` | LiteLLM，可选 | 只有采用 LiteLLM 组合部署时才使用 |

这几个 Key 应当互不相同。不要把 `MAAS_API_KEY` 直接提供给业务客户端，也不要把真实 Key 写进代码、截图、文档或提交到 Git。

## 2. 当前服务怎么打开

当前本机服务地址：

- 管理后台：<http://127.0.0.1:8787/>
- OpenAI 兼容 API Base URL：`http://127.0.0.1:8787/v1`
- 健康检查：<http://127.0.0.1:8787/health>

打开管理后台后：

1. 在右上角填写 `.env` 中的 `ADMIN_TOKEN`。
2. 点击“连接”。
3. 页面显示“已连接 · v0.4.9”这类 semver 版本即表示成功。
4. 如果刚升级过页面，按 `Ctrl+F5` 强制刷新。

`ADMIN_TOKEN` 只用于后台登录；调用模型时应使用 `ROUTER_ACCESS_KEY`。

## 4. 最快的 Auto 调用方式

### PowerShell

先把客户端 Key 放入当前终端环境变量：

```powershell
$env:ROUTER_ACCESS_KEY = "你的ROUTER_ACCESS_KEY"
```

调用 Auto：

```powershell
$headers = @{
  Authorization = "Bearer $env:ROUTER_ACCESS_KEY"
  "Content-Type" = "application/json"
  "x-session-id" = "conversation-001"
}

$body = @{
  model = "auto"
  messages = @(
    @{ role = "user"; content = "分析这段 Java 代码的并发问题，并给出修复方案" }
  )
  stream = $false
  max_tokens = 1024
} | ConvertTo-Json -Depth 10

Invoke-RestMethod `
  -Method Post `
  -Uri http://127.0.0.1:8787/v1/chat/completions `
  -Headers $headers `
  -Body $body
```

路由器会分析任务，选择已启用的自建模型之一，再把 MaaS 的 OpenAI 格式响应原样返回。

### Python OpenAI SDK

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:8787/v1",
    api_key=os.environ["ROUTER_ACCESS_KEY"],
)

response = client.chat.completions.create(
    model="auto",
    messages=[
        {"role": "user", "content": "比较 Saga、TCC 和本地消息表的优缺点"}
    ],
    max_tokens=2048,
)

print(response.choices[0].message.content)
```

### 流式输出

只需要把 `stream` 改为 `true`。服务会透传 MaaS 的 SSE 数据，不缓存完整回答。

## 5. Auto 和显式模型的区别

Auto 请求：

```json
{
  "model": "auto",
  "messages": [{"role": "user", "content": "今天星期几？"}]
}
```

显式模型请求：

```json
{
  "model": "qwen36-35b",
  "messages": [{"role": "user", "content": "今天星期几？"}]
}
```

行为差异：

- `auto` 会执行难度分析、模型评分、健康过滤和 fallback。
- 显式模型不会自动换模型，便于兼容原有业务和做模型对照测试。
- 当前生态模型 `Minimax-M3` 已禁用，不会进入 Auto 候选和 fallback。

查看可用模型：

```powershell
Invoke-RestMethod http://127.0.0.1:8787/v1/models
```

## 6. `x-session-id` 怎么用

同一段对话建议每次请求携带相同的 `x-session-id`：

```text
x-session-id: customer-service-session-10086
```

作用：在模型仍然健康且满足要求时，同一会话尽量继续使用同一个模型，减少多轮对话中模型风格突然变化。

- 同一会话：使用相同 ID。
- 新会话：生成新的 ID。
- 希望每次独立选择：不传该请求头。

当前默认粘性时间为 30 分钟。

## 7. 怎么看一次请求为什么选这个模型

在管理后台的“单题路由解释”中：

1. 输入问题。
2. 根据请求情况勾选“工具调用”“严格 JSON”或“流式输出”。
3. 点击“计算选择”。

页面会显示：

- 建议模型与实际模型。
- 任务类型、难度和判断置信度。
- `rules`、`rules_semantic_shadow` 或 `semantic` 判断方式。
- 推荐推理强度：`off`、`standard`、`high`。
- 难度由哪些信号构成。
- 每个候选模型的评分和质量门槛。
- fallback 顺序。
- 如果触发语义复核，会显示规则结果和复核结果的差异。

示例预期：

- “今天星期几？”：简单任务，难度约 `0.08`，`reasoning=off`，不触发语义复核。
- 多模型 MaaS 路由架构方案：复杂推理任务，难度通常大于 `0.7`，推荐更高质量模型和 `high` 推理强度。

预演不会调用最终回答模型；但低置信度问题可能调用一次语义分类模型，因此会产生少量上游调用成本。

## 8. 业务策略怎么配置

### 策略预设

| 预设 | 适合场景 | 行为 |
|---|---|---|
| 均衡模式 | 默认生产流量 | 综合质量、成本和速度 |
| 成本优先 | 批处理、内部低风险任务 | 质量达标后更积极选择便宜模型 |
| 质量优先 | 复杂分析、重要文案 | 提高质量门槛，容忍更高成本和时延 |
| 速度优先 | 在线客服、交互问答 | 更偏好低首字和低完成时延模型 |

选择预设后先看“调整影响预估”，不要直接发布。

### 主要参数

- 最低质量目标：低于该质量分的候选不会优先选择。
- 成本敏感度：越高越偏向低成本指数模型。
- 速度敏感度：越高越偏向低时延指数模型。
- 自建偏好：满足能力与质量要求时，为自建模型增加选择优势。
- 复杂任务质量加严：复杂任务在最低质量目标上额外提高门槛。
- Auto 生效流量：只有该百分比的请求真正采用 Auto 建议，其余走 Shadow 模型。

质量分、成本指数和时延指数是模型之间的相对比较值，不是金额和毫秒。建议由基准测试结果统一校准，不要凭感觉频繁修改。

## 9. 两种 Shadow 不要混淆

系统有两个独立的 Shadow：

### Auto 主路由 Shadow

“运行状态 → 仅观察，不改变模型”：

- 系统照常计算建议模型。
- 实际请求固定发给 `shadowModel`。
- 用于验证整体 Auto 策略是否可靠。

### 语义复核 Shadow

“语义复核运行方式 → 仅观察分歧”：

- 只有规则置信度较低的请求才调用语义分类（当前 `deepseekv4-flash`，可换自训练小模型）。
- 分类在后台执行，不增加主请求等待时间。
- 只记录规则与语义分类的分歧，不改变线上模型选择。

推荐初期两个都使用 Shadow。语义复核至少积累 200～500 条人工检查样本后，再考虑切换为“正式采用复核结果”。

## 10. 模型参数怎么填

模型表中：

- 默认质量：0～1，相对效果评价，应来自业务评测。
- 成本指数：越小越便宜，用于路由评分。
- 时延指数：越小越快，用于路由评分。
- 输入/输出单价：真实的元/百万 Token，用于预算估算。
- P95 总时延：95% 请求能够在该毫秒数以内完成，用于运营观测。

建议把四个模型的成本、时延做归一化：最快或最便宜的模型接近 `0.1`，最慢或最贵的模型接近 `1.0`，其他模型按比例填写。

真实单价为空时，系统会把请求记为“未定价请求”，不会误认为成本为零。

## 11. 每日预算保护怎么开

启用前必须先填写所有已启用模型的输入和输出单价。

操作步骤：

1. 填写模型真实单价。
2. 填写“每日预算（元）”。
3. 将“开始保护的预算比例”保持在 `0.9` 左右。
4. 勾选“启用每日预算软保护”。
5. 查看发布影响后安全发布。

达到阈值后，系统会提高成本因素的影响，并把推理强度从 `high` 降为 `standard`、从 `standard` 降为 `off`。

预算是软保护，不是财务结算，也不会直接拒绝请求。当前金额根据输入估算、请求的 `max_tokens` 和模型单价计算；对于流式响应，不解析最终账单 Token。正式计费应以 MaaS 或 LiteLLM 的实际 usage 为准。

预算账本保存在 `data/budget-ledger.json`，按 `Asia/Shanghai` 自然日统计。

## 12. 推理强度开关怎么用

页面显示的 `off / standard / high` 首先是路由建议，不代表一定向上游发送了额外参数。

当前安全默认值为关闭，因为不同 MaaS 模型支持的参数名和值可能不同。只有同时满足以下条件才会向上游发送：

1. 全局“向已验证模型发送推理强度参数”已启用。
2. 对应模型在配置中标记 `reasoningControl.verified=true`。
3. 已经用该模型真实验证参数不会导致 400、输出异常或费用失控。

在四个模型逐一验证完成前，保持关闭。

## 13. 推荐上线流程

1. 保持生态模型禁用，只测试自建模型。
2. 主路由设为 Shadow；语义复核也设为 Shadow。
3. 运行基准测试并人工评阅复杂题：

   ```powershell
   npm run benchmark -- --dry-run
   $env:BENCHMARK_CONCURRENCY = "2"
   npm run benchmark
   ```

4. 根据结果更新质量、成本指数、时延指数和真实单价。
5. 收集至少 200～500 条实际任务，重点检查复杂任务是否被低估。
6. 主路由改为 Active，先设置 5%～10% 生效流量。
7. 观察错误率、fallback、自建承载率、语义分歧率和业务反馈。
8. 逐步扩大到 25%、50%、100%；每一步都先做影响模拟。
9. 最后再评估是否启用语义复核 Active、预算保护和推理参数。

点击“安全发布”后，旧版本自动保存到 `config/history/`。高影响调整会要求二次确认。

## 14. 怎么读取路由响应头

每次成功响应都包含：

| 响应头 | 含义 |
|---|---|
| `x-router-selected-model` | 实际调用的模型 |
| `x-router-suggested-model` | Auto 评分建议的模型 |
| `x-router-policy-version` | 当前软件版本 |
| `x-router-shadow` | 是否未真正采用 Auto 建议 |
| `x-router-route-method` | `rules` 或 `semantic` 等判断方式 |
| `x-router-reasoning-level` | 推荐或实际采用的推理强度 |

PowerShell 查看响应头：

```powershell
$response = Invoke-WebRequest `
  -Method Post `
  -Uri http://127.0.0.1:8787/v1/chat/completions `
  -Headers $headers `
  -Body $body

$response.Headers
$response.Content
```

## 15. Fallback 和熔断行为

- 只有 `model=auto` 会自动 fallback。
- 408、429、部分 5xx 和网络错误会尝试下一个候选模型。
- 连续失败达到阈值后，模型进入 OPEN 熔断状态。
- 冷却结束后只允许一个 HALF_OPEN 探测请求。
- 探测成功恢复 CLOSED；失败则重新进入 OPEN。
- SSE 已经开始输出后不会换模型重放，避免给客户端重复内容。

## 16. Docker 启动

直接连接 MaaS：

```powershell
docker compose up --build -d
docker compose logs -f auto-router
```

停止：

```powershell
docker compose down
```

容器只发布到宿主机 `127.0.0.1:8787`。`config/` 和 `data/` 已挂载到宿主机，配置和预算账本不会因容器重建丢失。

需要 LiteLLM 时：

```powershell
docker compose -f compose.litellm.yaml up --build -d
```

LiteLLM 负责协议适配、限流、计费和多实例调用；Auto Router 继续负责模型之间的业务选择。详细说明见 [LiteLLM 集成说明](litellm.md)。

## 17. 常见问题

### 后台显示“连接失败”

- 确认填写的是 `ADMIN_TOKEN`，不是 `ROUTER_ACCESS_KEY`。
- 修改 `.env` 后必须重启 Node 服务。
- 检查 Token 前后是否带空格。

### API 返回 401

- 客户端 Authorization 应使用 `ROUTER_ACCESS_KEY`。
- 格式必须是 `Authorization: Bearer <Key>`。

### `/health` 显示 `upstreamConfigured: false`

`.env` 缺少 `MAAS_API_KEY`，或者服务没有在项目目录下启动。

### 调整参数后看不到变化

- 点击“安全发布”，不能只修改输入框。
- 检查右上角软件版本是否与 `package.json` 一致。
- 浏览器按 `Ctrl+F5`。
- 如果 Auto 主路由处于 Shadow，建议模型会变化，但实际模型仍是 `shadowModel`。

### 预算一直显示 0

- 预算功能是否启用。
- 每日预算是否大于 0。
- 所有启用模型是否填写了输入、输出单价。
- 查看是否存在“未定价请求”。

### 语义复核没有触发

高置信度的简单题或明确复杂题不会复核。只有规则置信度低于配置阈值、且文本长度达到最低要求时才触发。

### 语义分类模型失败会不会影响回答

不会。分类超时、格式错误或上游失败时，会安全回退到原规则判断；Shadow 模式下主请求本来就不等待分类。

## 18. 当前生产化边界

- 请求、健康和语义分歧指标仍主要保存在内存，服务重启会清空。
- 预算是估算值，不是最终账单。
- 模型质量分需要持续用真实业务样本校准。
- 对外网开放前必须增加 TLS、网关访问控制、限流、租户隔离和持久化监控。
- 不要在没有 Shadow 数据和回滚方案的情况下直接把高影响策略发布到 100% 流量。
