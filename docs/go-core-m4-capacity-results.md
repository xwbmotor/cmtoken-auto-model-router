# M4 同配额开放负载实测

本轮补齐同等硬配额、混合输入开放负载和分钟级 SSE 验证，但**当前 Go + Node 适配器组合未体现容量优势，不据此进入生产切换**。Node 在所测 50/150/300 RPS 三档均完整交付所有计划请求；Go 在 50 RPS 完成交付，150/300 RPS 档分别只发起并完成计划量的 88.64% / 43.11%，完整吞吐约 127.47 / 121.76 RPS。其余为发压器达到待处理上限或迟到阈值后的丢弃，不能因已发起请求 HTTP 错误为 0 而称为全量成功。

Go 高档位的完整请求 P95 超过 2 秒，同时存在 CPU 限流。这是本次观测，当时尚未通过剖析证明瓶颈属于 Go runtime、适配器、账本或其他环节。后续 [专项排查](go-core-m4-diagnosis.md) 已定位 Go L1 长文本正则扫描为主要瓶颈，优化尚未实施。不得将其归因为语言本身。三轮合并分位数是描述性统计，未做显著性检验；这也不是精确容量极限搜索。

两条网关路径各 32 条、60 秒 SSE 全部完成；全实验唯一上游调用与模拟输入检查通过，无 OOM kill。总计 30 组测量、39,477 条发起请求（包含 12 条预检、96 条 SSE），另有 5,631 条计划请求未发起。原始证据保留所有发起样本及每组丢弃计数。

每个服务组均限制为 1 CPU、512 MiB 内存且不提供额外 swap。Go 组包含 Go runtime、Node 适配器和真实 Node 管理服务。模拟上游、公共 TCP 入口和发压器在配额之外。

持久化语义并不完全相同：Node 预算更新加入异步 JSON 写入队列，决策日志异步追加；Go 预占、结算 WAL 与审计各执行同步落盘。相同硬资源配额不等于相同持久化保证，此表比较的是当前两套实现的完整路径，不能用于断言语言本身的快慢。
