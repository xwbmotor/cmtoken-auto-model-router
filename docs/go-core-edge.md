# Go 业务链路与生产切换验证

生产已于 2026-09-11 完成 Go v0.14.8 入口切换，最新状态与证据见 [生产切换验收](go-core-production-v0.14.8.md)。本页保留早期实验、未通过候选和 v0.14.7 回滚历史；历史状态不代表当前生产。

## 已实现的接口与状态衔接

- 已保留两条显式入口：原 Node HTTP edge，以及可选的 Go 原生公网入口。后者直接承接标准 Bearer JSON/SSE 请求；管理页面、CORS、压缩正文和兼容请求通过固定 loopback Node 服务处理。任何路径都不会在 Go 调用后自动退回 Node 重试。
- Go 执行原生分析、选模、会话约束、并发额度、健康熔断、租户模型范围、重试、非流式和 SSE 转发。补测和业务共享 Go 的模型额度。
- Node 向 Go 传入当前配置版本及各任务的市场调整值；私有上下文和边缘令牌不转发给模型服务。
- Go 原生入口将所有尝试汇总为一次完成事件，回传 key/会话指纹、延迟范围摘要、正文及有界回答；不回传原始凭据或会话 ID。Node 继续按原策略决定正文留存和 Judge。共享分桶密钥通过内部 HMAC 证明核对。
- Go 向固定 Node 内部接口回传尝试结果和语义复核。回传重试按不透明请求 ID、尝试序号和载荷摘要去重，不重新调用上游。
- Node 继续记录决策、真实正文 TTFT、流式完整性、成本观察、语义复核与 Judge。Go 返回的实际费用在 Node 中直接记为一次完成记录，不重复创建临时预占。
- 配置保存与 Go 发布串行执行。明确拒绝时恢复原始配置字节；不确定结果会暂停新业务请求，等待重新加载完成对账。导入和自动校准只在发布成功后替换内存配置。
- 关停先停止接收新业务，并等待上下文缓存过期、Go 在途请求、所有代际后台复核及结果回传，随后关闭监听并刷出记录；等待有上限。生产容器的停止宽限须覆盖业务排空与日志刷盘。
- 默认模式保留 Go WAL、检查点与审计的同步持久化。显式 `--node-cost-observation` 仅允许预算保护关闭且已连接可信 Node edge：成本观察由现有 Node 台账统一记录，Go 不重复记账。Node 沿用异步快照语义，不承诺金融账本级断电耐久性。预算开关和成本归属改变需受控迁移。
- 生产边缘链路的 L3 使用配置中的运行时预算；实验模式仍有独立的调用次数/token 限额，避免实验限制在生产长期运行后耗尽。

## 启用合同

Node 的环境变量：

| 变量 | 用途 |
| --- | --- |
| `AMR_GO_NATIVE_FRONT` | 设置为 `1` 启用原生完成事件接收；默认关闭 |
| `SEMANTIC_BUCKET_SECRET` | 原生入口必须与 Go 使用相同的稳定独立随机密钥 |
| `AMR_GO_CHAT_URL` | 固定 `http://127.0.0.1:<Go端口>/v1/chat/completions` |
| `AMR_GO_EDGE_TOKEN` | Node/Go 共享的独立随机内部令牌，至少 32 字符 |
| `AMR_GO_ADMIN_URL` | 固定 `http://127.0.0.1:<Go端口>` |
| `AMR_GO_ADMIN_TOKEN` | Go 受保护鉴权文件中的管理令牌 |
| `AMR_GO_RUNTIME_CONFIG` | 已初始化的运行时快照路径；不得与源 router.json 相同 |
| `ADMIN_TOKEN` | 原管理端令牌，继续保留 |

Go 需要 `AMR_GO_EDGE_URL=http://127.0.0.1:<Node端口>/internal/v1/go-events` 及同一个 `AMR_GO_EDGE_TOKEN`。其他业务鉴权、语义分桶及上游配置遵循已有候选实例合同。所有凭据只由宿主机受保护配置注入。

原生入口另需 Go `--public-listen <IP>:8787 --node-origin http://127.0.0.1:8789`，同时 Go 私有监听仍为 `127.0.0.1:8791`。非 loopback 公网监听必须显式使用 `--candidate`。Node 监听仅 loopback，公网不暴露 `/internal/`。

Node 和 Go 必须能读同一份快照，Node 负责原子写入。快照文件为 0600；容器用户和挂载权限必须与此一致。Go 的账本和审计使用独立状态目录。Node 成本归属模式必须使用新的 Go 状态路径，保留 `.node-observation` 标记；该模式下不能把空 Go WAL 导出覆盖 Node 台账，回滚继续使用 Node 原有成本文件。

监控新增 `amr_go_core_available` 与 `amr_go_edge_report_errors_total`，分别表示运行时可用性及回传错误累计数。原管理指标继续保留。

## 性能判断与限制

首个完整链路标准实验：[34562408026](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34562408026)，提交 `3804a572fb4372304fb69654ce138b67414fb2d5`。

每组 2 CPU、512 MiB；同一组内包含 Go 与真实 Node 入口/管理进程。预算保护关闭但保留成本观察和决策日志；Judge、语义复核及限流关闭。100/300 RPS 各 3 轮、每轮 10 秒，另测 32 路 60 秒 SSE。

| 路径 | 100 RPS P95 | 300 RPS P95 | 300 RPS 平均 CPU 核 |
| --- | ---: | ---: | ---: |
| Node | 15.47 ms | 20.73 ms | 0.71 |
| Node 入口 + Go | 539.04 ms | 632.35 ms | 0.99 |

这次结果不满足切换条件。Go 组还有 37 个计划请求未发起，不能仅凭已发起请求零错误宣布通过。

随后同一主机采用 native / edge / edge / native 交错实验：[34563653662](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34563653662)。原生 Go 在 300 RPS 的 P95 为 22.11/22.90 ms、CPU 为 0.66/0.67 核；相应 Node P95 为 31.89/36.08 ms、CPU 为 0.99/1.00 核。但完整边缘链路仍有明显额外开销。原生 Go 路径未经过完整 Node 记录处理，不能用其结果替代生产链路验收。

短时剖析显示账本写盘锁等待、Node 日期格式化、文件操作和 GC 均有开销。去掉未使用的预算快照读取后，交错对照未显示稳定收益，不能将它宣称为已解决根因。重复费用投影优化后仍未达到条件，随后继续验证原生公网入口。

## Node 成本归属模式与测试转发器检查

[34572353514](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34572353514)，提交 `773e24c7d66d780a5e127b55a7d6fd275545179f`，显式启用 `--node-cost-observation`。两轮 2 CPU / 512 MiB 标准实验全部计划请求发起并完整交付，决策记录无缺失和重复，32 路 60 秒 SSE 均通过。300 RPS 下 Node P95 为 21.53 / 21.82 ms，Go 为 60.62 / 61.10 ms；Go CPU 为 0.87 / 0.89 核，Node 为 0.73 / 0.75 核。该结果仍不构成切换依据。

第一轮原始样本显示，Go 首字节 P95 约为 19.84 ms，首字节至响应结束 P95 约为 41.64 ms；Node 对应约 20.50 ms 与 0.04 ms。测试公共 TCP 转发器未设置 `TCP_NODELAY`，而 Go 在 Node 完成事件确认前显式刷出正文，最终 HTTP 结束标记随后发送。已增加两条转发路径双向关闭 Nagle 的默认设置，并保留 `--relay-nagle` 做同二进制 ABBA 对照；需要实验确认，不能仅据这一时延形态断言根因或宣称 Go 更快。

后续 [34573703415](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34573703415) 用同一业务二进制完成 Nagle / no-delay / no-delay / Nagle 对照。300 RPS 下 Go P95 依次为 59.72 / 21.26 / 21.82 / 59.71 ms；对应 Node 为 21.86 / 19.10 / 19.34 / 21.89 ms，全部请求和日志完整。这确认公共转发器引入了主要固定等待，但修正后 Go 仍稍慢，且 300 RPS CPU 约 0.75–0.77 核，高于 Node 的 0.69–0.70 核。

[34573806049](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34573806049) 的 600/900 RPS 探索性检查也未证明容量优势；两个服务均有大量计划请求未发起。Go 完整吞吐约 343–352 RPS，Node 约 404–441 RPS，不能用成功请求零错误掩盖未交付的计划负载。

[34574413773](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34574413773) 的修正链路剖析显示，原预占/结算等待已消除，Go 主要 CPU 来自 Unicode 解码、规则扫描和 JSON 处理。Go 分析阶段平均约 0.89 ms、P95 4.18 ms；Node 完成事件往返平均约 1.72 ms。针对分析热点新增双字节 UTF-8 前缀过滤和经过全码点验证的折叠快捷路径。本地长历史微基准从约 3.1 ms 降至 1.7 ms，但微基准不能替代完整链路验收。

## 早期切换准备与门槛（历史记录）

### 最近的标准复测

规则扫描优化的同主机 ABBA 对照 [34575012092](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34575012092) 显示，Go 300 RPS P95 从 21.25 / 21.10 ms 降至 19.62 / 19.64 ms，CPU 从 0.73 / 0.75 核降至 0.69 / 0.68 核。此后复用已验证的请求字段，完整 Go 差分与 Native Node 成本归属联调通过。

但最新两次 CI 标准实验 [34575978017](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34575978017) 仍未证明整体优势：Node 300 RPS P95 为 22.70 / 19.14 ms，Go 为 21.82 / 20.78 ms；Node CPU 为 0.73 / 0.64 核，Go 为 0.82 / 0.76 核。两组每次均完整交付 12,036 个请求并生成同数决策记录，无缺失、重复、错误或发压丢弃。32 路持续 SSE 完整，但 Go 采样内存峰值约 240–245 MiB，高于 Node 的 128–131 MiB。

该 CI 主机只有 2 个逻辑 CPU，而每个服务组配额也是 2 CPU，配额外的模拟上游和发压器仍竞争同一主机资源。新增 `--isolated-host` 模式，在至少 4 CPU 主机上限定服务组轮流使用 CPU 2（1 CPU / 256 MiB），发压器及模拟上游使用 CPU 3；模拟上游另限 1 CPU / 192 MiB，各容器 CPU shares=64。该模式不改变其他宿主机进程的亲和性，不能声称独占物理 CPU，也不能直接等同于 2 CPU / 512 MiB 的生产容量。

2026-09-11 08:44 UTC 的首次目标主机隔离标准实验完整通过请求、日志与 SSE 完整性检查。300 RPS 下 Node / Go 的合并 P95 为 238.72 / 191.23 ms，平均 CPU 为 0.84 / 0.78 核；100 RPS P95 为 45.65 / 45.08 ms。Go 的 SSE 首字节 P95 为 132.15 ms，高于 Node 的 83.20 ms；采样内存峰值为 212.72 / 113.57 MiB。这是有收益也有退化的结果，不应表述为全方面更快。原始 JSON SHA256 为 `419abd0b86cf575e0d02e2237dbf9c182bebb9dc8f7465a1483dbf5cefe44c28`，二进制对应 `412bb13` 的源码归档。

08:52 UTC 的第二次独立启动同样全部完整：300 RPS 的 Node / Go P95 为 279.83 / 213.84 ms，CPU 为 0.85 / 0.78 核；100 RPS P95 为 48.94 / 44.84 ms。但 300 RPS P99 为 371.83 / 468.71 ms，SSE 首字节 P95 为 85.51 / 132.72 ms，采样内存峰值为 139.49 / 211.42 MiB。两次各有 12,036 个业务路径完整请求与同数日志；原始第二次 JSON SHA256 为 `9057f8c1b7556f696784c35f0b787729fd1104e49a5342ece7e655393edc4b47`。当前可确认的是此隔离配置下 CPU 和合并 P95 改善，P99、SSE 与内存仍有代价，尚不构成稳定整体优势。

同二进制短时剖析中，JSON 编解码及原始值重排仍占明显 CPU：标准编码会重复扫描已由入口验证的历史内容。新增仅用于 HTTP JSON 的原始值对象编码，保留所有字段与数值，非法 UTF-8 回退标准编码器；转发及完成事件均使用该路径。长历史编码本地微基准从约 403 μs 降至 118 μs，JSON 语义差分及网关回归通过，完整性能收益仍待对照。

### 发布与迁移准备

`go-core/deployment/prepare_native.py` 在目标主机核对三个正式镜像的 OCI revision、当前 Compose 与运行容器环境、预算保护关闭及首次迁移条件，生成独立的受保护目录。它保存原始 Compose、环境文件和 router 配置，使用正式 Node 镜像导出初始 Go 快照，并生成共享网络的三服务 Compose；不会修改生产文件或应用部署。三服务实际迁移演练已通过 [34585205320](https://github.com/xwbmotor/cmtoken-auto-model-router/actions/runs/34585205320)：测试调用同一准备脚本，完成 Node 基线、Go 接管、Go 重启及恢复 Node；8 个请求费用和日志逐项一致，私有接口不对外开放。演练使用模拟上游与模拟分类服务，不能证明真实分类质量。正式发布镜像及目标主机上线验收仍待完成。

1. 完整功能链路达到相对于 Node 的可接受性能；保留原始请求数据、完整交付率和资源证据。
2. 准备正式版本标签及 Node、Python、Go 三个匹配提交的镜像；通过正式发布检查。
3. 在目标服务器保存原 compose、配置、镜像及状态，并验证实际切换与回滚。
4. 保留生产 Judge、语义复核、补测、校准和业务参数；验收真实非流式/SSE、记录、配置发布和重启恢复。
