# M4 L1 扫描优化与同机验证

> 历史阶段记录：下文保留当时的版本、实验条件和待办。“未切换生产”等描述只适用于记录时点；v0.14.8 已完成生产切换，见 [验收记录](go-core-production-v0.14.8.md)。

后续已完成[第二轮文本分配与扫描优化](go-core-m4-tail-optimization.md)。下文保留第一轮原始数据；第二轮采用同机重新运行的基线，不与本页跨轮混算优化降幅。

优化已实现并通过同机对照。在本轮混合输入、1 CPU / 512 MiB 条件下，300 RPS 档的 Go 完整吞吐从 132.63 提升至 299.25 RPS（约 2.26 倍），9,000 个计划请求全部发起并完成；发压丢弃从 4,764 降为 0，P95 从 2,373.62 降至 163.82 ms（下降约 93.1%）。长历史分析组件约提速 5.42 倍。优化后 32 路、60 秒 SSE 完整通过。

本次解决了已测混合输入在 150/300 RPS 档的发压丢弃问题，但高负载尾延迟仍有差距：同一优化后阶段 Node 的 300 RPS P95 为 72.34 ms，低于 Go 的 163.82 ms。不能据此宣称 Go 全面优于 Node 或已经满足生产 SLO。生产没有切换；后续仍需按真实负载与约定目标验收。

## 同机实测

每档三轮合计；完整吞吐包含请求排空，P95/P99 合并完整成功请求，错误和未发起数单独核对。前后两版已发起请求均无 HTTP/内容错误；旧版的发压丢弃仍计入未完成计划量，不能称为全量成功。

| 目标 RPS | Go 完整吞吐：旧 → 新 | 完整请求/计划：旧 → 新 | 未发起：旧 → 新 | P95 ms：旧 → 新 | P99 ms：旧 → 新 |
|---|---:|---:|---:|---:|---:|
| 150 | 131.13 → 149.89 | 4045/4500 → 4500/4500 | 455 → 0 | 2186.82 → 22.99 | 2465.10 → 27.80 |
| 300 | 132.63 → 299.25 | 4236/9000 → 9000/9000 | 4764 → 0 | 2373.62 → 163.82 | 2896.44 → 236.71 |

| 目标 RPS | Go 平均 CPU 核：旧 → 新 | Go cgroup 采样峰值 MiB：旧 → 新 | CPU 限流周期：旧 → 新 |
|---|---:|---:|---:|
| 150 | 0.90 → 0.45 | 138.00 → 69.15 | 167 → 0 |
| 300 | 0.89 → 0.76 | 163.12 → 98.72 | 186 → 2 |

CPU 为组内所有进程累计 CPU 用量除以采样时间，内存包含 cgroup 记账缓存且可能遗漏瞬时峰值；它不是 RSS。两版均无 OOM kill。150/300 RPS 档的 direct 和 Node 控制组均完成全部计划请求。Node 吞吐分别从 149.90/299.69 变为 149.92/299.73 RPS；300 RPS Node P95 从 60.99 变为 72.34 ms，说明即便同机仍存在阶段波动。

两版 Go 各 32 条、持续 60 秒 SSE 均完整完成、上游调用各 32 次。Go 首字节 P95 从 239.46 降为 120.34 ms，完整时长 P95 从 60,286.00 变为 60,153.86 ms；这里的首字节是模拟上游的传输观测，不是真实模型生成性能。

组件基准各两轮如下，单位为每次调用的平均耗时。Linux 宿主为 AMD EPYC 7763，Go 1.27.1。

| 输入 | 旧版 ms/op，两轮 | 新版 ms/op，两轮 | 两轮均值提速 |
|---|---:|---:|---:|
| 短文本 | 0.064365 / 0.062064 | 0.018165 / 0.018425 | 约 3.46 倍 |
| 长历史 | 17.625231 / 17.738187 | 3.264024 / 3.260614 | 约 5.42 倍 |

长历史每次分配量仍约 0.97 MB，未宣称消除了容量估算与 JSON 处理的分配。以上提速是本次观测，不是所有自定义规则、请求长度或目标环境的保证。

## 实现范围

针对 [专项排查](go-core-m4-diagnosis.md) 定位的 Go L1 长文本正则热点，本次修改 [fast_regex.go](../go-core/internal/analysis/fast_regex.go)、[analysis.go](../go-core/internal/analysis/analysis.go) 与 [regex.go](../go-core/internal/analysis/regex.go)。没有调整模型策略、预算与审计同步落盘、适配器合同或生产入口。

固定词及可有限展开的表达式在配置构建时生成前缀树，按原表达式的分支优先级返回最左匹配及原文本字节位置。扫描仍保留所有匹配和信号计数，不截断历史，不因复杂度贡献已经封顶而少计信号。每个表达式最多展开 256 个分支；空匹配、锚点、无限重复、混合大小写作用域及超出安全范围的表达式保留原 Go 正则路径。

复杂表达式从语法树提取“匹配成功时至少必须出现一个”的字面词集合。缺失所有必要词时直接返回未命中；存在候选时仍交给原正则验证。大小写预筛选使用 Unicode SimpleFold 的等价类，可产生额外候选，不把候选直接认定为命中。原有 UTF-16 代理单元映射、任务顺序、自定义规则校验与复杂表达式行为继续保留。配置加载后匹配器只读，不缓存请求内容。

另外，文本没有否定范围时直接返回否定检查未命中，避免重新扫描获胜任务；两个工具名正则移至初始化阶段。预算 WAL 与审计的同步落盘实现保持不变。

## 行为验证

- 新增匹配器对照测试，以原 Go 正则为独立判据，比较布尔命中、匹配文本、字节区间以及 `n=-1/0/1/3` 的行为。覆盖分支优先级、贪婪/非贪婪可选项、重叠、空匹配、大小写作用域、Kelvin sign、long s、希腊字母、代理单元和复杂规则回退。
- 本地 15 秒模糊测试执行 50,992 次，未发现差异；种子用例同时加入普通 CI。模糊测试是有限覆盖，不能替代全部语义证明。
- 本地 3,145 条选模、1,153 条原生分析、852 条语义复核差分均无差异，共 5,150 条。运行时预算恢复、重试、热更新、管理桥接和离线账本往返也通过。
- 当前候选的 Linux CI 再次通过上述 5,150 条差分、87 项 Go 测试和 8 个模糊测试种子，`go vet` 与 `go test -race` 通过；完整对照和容量冒烟均通过。

## 同机对照方法

工作流 `optimization` 在同一个 Linux runner 构建旧版 `f30e8d7eddd290732b66210c9b6fbf8123f1a192` 与新版 `cd02f356d165c5bf1ddd73048c52bc4167fb73d8`，先运行各两轮分析组件基准，再依次运行旧版、新版完整网关实验。两次网关实验各自包含 direct、Node、Go 三条路径，并在各轮轮换路径顺序。

两版均为每组 1 CPU / 512 MiB、10 秒发起窗口、150/300 RPS、每档三轮，短文本/长历史/工具/图片各占四分之一。两版均校验 32 路、60 秒 SSE。Go 组包括 Go runtime、Node 适配器和真实 Node 管理服务，公共入口、模拟上游和发压器在配额外。Node 账本异步写入与 Go 同步落盘的区别仍存在，因此不能将 Node/Go 差异解释为语言本身的快慢。

旧版与新版测试按固定先后次序执行，并非随机交错的统计试验。Node 对照与同机环境用于观察环境变化，但不能完全消除时序、宿主调度、缓存与文件系统影响。组件基准在宿主上运行，不能直接当成 cgroup 网关吞吐；容量结论以完整请求的计数、错误、发压丢弃、尾延迟和资源观测为准。
