# Auto 标杆对照与持续优化路线图

核验日期：2026-09-08。基线为本轮开发开始时的 v0.14.1 代码与项目文档；本轮正在增加的能力单列，是否已上线以对应版本的发布与部署验收记录为准。本文的窗口、阈值与试验规模是设计建议，不是已验证的生产参数。

## 1. 建设方向

优先把 Auto 建成“能解释、能验证、能回退”的业务路由：质量和协议能力确定可用候选，真实时延与容量决定当下如何分配，运营界面解释异常与调整效果。热力图是入口；真正有价值的是从可信测量到受控决策的闭环。

本轮范围是分组时延观测、热力图、受预算约束的少量补测及影子评分。影子评分只记录候选变化，不改变实际选模，也不自动重写质量分。新的在线算法、预测收益与全池容量控制仍需后续验证。

## 2. 标杆值得借鉴的部分

以下是官方资料的简短归纳；后续方案是结合本项目约束的设计判断，并非这些产品对 Auto 收益的背书。

| 标杆与来源 | 可借鉴机制 | 不直接照搬的原因 |
| --- | --- | --- |
| [LiteLLM Router](https://docs.litellm.ai/docs/routing) | 时延统计窗口、近最快部署候选缓冲、多部署限额和故障处理 | 同一模型多部署与不同能力模型不是同一个选择问题；不能凭速度绕过质量、租户、工具及思考预算限制。官方也没有将时延策略列为所有生产场景的默认最优解 |
| [vLLM Metrics](https://docs.vllm.ai/en/latest/design/metrics/) | 分开首 token、生成间隔、完整请求耗时，关联运行与等待请求数 | 推理服务内部计时不等于客户端感知计时；需核对实际版本和指标权限。模型推理 token、思考片段、正文及 SSE 数据包不能混称“首字” |
| [Envoy Adaptive Concurrency](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/adaptive_concurrency_filter.html) | 以基准时延与近期时延偏离调整并发，并保留缓冲 | 官方要求控制目标集群请求并发；共享 MaaS 池若存在旁路流量便不满足这一前提。LLM 请求长短差异大，不能直接套用完整 RTT；也不照搬可能引发 503 的基准测量流程和自动重试建议 |
| [Grafana Heatmap](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/visualizations/heatmap/) | 用时间与分布展示异常，通过提示信息说明数据 | 用户截图是“模型×小时”的聚合矩阵，和“时间×时延桶”的分布热力图不同。前者易定位模型，后者更适合找长尾；第一版保留矩阵，不必引入整套监控平台 |

## 3. 当前能力与真实差距

现状依据：[路由实现](../src/router.mjs)、[健康状态](../src/health.mjs)、[代理与计时](../src/server.mjs)、[管理台](../public/index.html)、[模型评分与并发调度](model-load-and-scoring.md)、[离线学习流程](routing-learning-workflow.md)。这里确认的是代码能力，未据此声称当前生产已启用全部开关。

| 领域 | 基线已实现 | 差距与建设性意见 | 优先级 / 验收依据 |
| --- | --- | --- | --- |
| 时延观测 | 首正文、首输出、完整耗时、重试等记录；健康 EWMA | EWMA 混合成功/失败及不同完成语义。新增明确口径、来源和可比较分组；旧动态项保持兼容，待影子对比通过后替换 | P0：流式、非流式、失败、工具、取消、重试的计时归属可由固定事件序列核验 |
| 时延运营 | 模型健康及部分耗时展示 | 增加窗口 P50/P95、小时矩阵、样本量、过期和失败展示；空白不能按 0 ms 处理 | P0：接口聚合与原始有效样本对账；无样本、少样本、跨日、时区可验证 |
| 低流量补测 | 健康状态存在半开探针机制 | 定时性能补测独立于熔断恢复；统一短请求、错峰、最大并发、调用与 token 预算，生产拥堵时跳过；探测不代表业务质量 | P0：禁用时零主动调用，超预算停止，故障退避，无重叠任务，记录可区分业务与探测 |
| 动态选模 | 质量/成本/时延先验评分、健康惩罚、本进程负载扣分 | 新时延项先影子计算；不足/过期回退，限制最大扣分；后续以替换方式接入，避免旧新时延重复惩罚 | P0 影子 / P1 在线：影子开启前后相同输入的真实选择一致；在线试验另验收益与回退 |
| 容量控制 | 本进程原子占额、释放与满额过滤 | 登记全池容量不等于实时余量。扩副本前分配额度或建立共享计数；接上游队列后再判断是否需要自适应 | P1 条件触发：多副本合计不超额；取消、超时、进程故障的占额回收有依据 |
| 质量运营 | 质量先验、异步 Judge、离线评测与学习程序 | 先验与人工修订混合，不能统一称为“实测校准”；质量页展示来源、样本数、题集与模型版本，失败样本独立统计 | P0 文案 / P1 数据：每个对外质量结论可追溯到同口径证据；Judge 分数不自动当成功标签 |
| 效果证明 | 静态模拟与离线学习/比较工具 | 静态预估不能证明线上收益；补真实当前 Auto 对照、分组任务成功、完成费用和全链路时延 | P1：冻结方案和测试集，保留预测与结果隔离记录，报告不确定性及缺失样本 |
| 管理台布局 | 简单/专家模式、分区、页内跳转 | 模型表列多；质量文案与证据口径有偏差。默认列留业务关键指标，编辑与详情展开；“实测/模拟/影子”固定标识 | P0 口径 / P1 布局：常用分辨率可定位异常，键盘可操作，不靠颜色单独表达状态 |

## 4. 时延数据设计与决策边界

### 4.1 先把计时说清楚

- 请求级计时从网关收到请求开始，包含分类、等待、重试和上游调用；attempt 级从某次上游调用开始，记录该模型的表现。二者分开，不把前一次模型失败耗时全部归到后一次模型。
- 流式分别保存首输出与首正文。工具首输出有独立语义；没有正文时首正文是缺失值，不能替换成总耗时。非流式只从完整响应观察到结束，不能伪造 TTFT。
- 成功耗时分布与所有请求的错误/超时/取消计数并列。客户端取消与上游失败分开；请求数和尝试数分开。速度改善不能靠排除慢失败来证明。
- 输入长度若使用估算 token，应标记为估算；实际 usage 缺失不填 0。缓存、思考模式和输出长度影响比较，字段未知保留 unknown。

建议先按模型/上游标识、流式形态、思考模式、输入长度档及业务/探测来源划分。不要第一版叠加全部任务小类和租户，避免样本极度稀疏；合并回退时保留当前实际采用的分组粒度。

### 4.2 近期统计和小时规律分工

建议用短窗发现变化、中窗补足样本、小时矩阵解释规律。5/30 分钟只是初始候选；窗口长度应通过实际请求频率验证。P95 最低展示样本数是产品门槛，不能声称达到门槛就获得统计可信性；小样本显示样本量和不足标记。小时均值、小时 P95 都不能再简单平均得到全天指标，应回到全日样本或可合并直方图。

工作日/周末使用明确时区；法定调休若未接日历，只标“周一至周五/周六周日”，不暗示已识别法定工作日。按模型版本、上游或关键参数变化区分新旧基线。

### 4.3 从影子到在线

影子事件保存实际候选集、实际选择、影子选择、采用的指标/窗口/样本数/更新时间、回退原因与扣分变化。影子选择没有实际作答结果，不能据此计算“已节省多少时延”。

进入在线试验前，要完成同类请求受控对照：按会话稳定分组，避免同一会话在策略间来回跳；冻结版本、质量门和费用口径。报告业务成功率、首正文与完整耗时分布、超时率、每个成功任务总费用，以及路由自身新增开销。重试和分类/Judge/探测等成本按明确归属计入。

不要凭“观测一周”自动全量。先以业务可接受的退化幅度和改善目标估算所需独立样本，覆盖高峰与非高峰；样本不足就保持影子。在线小流量仅在门槛满足时开启，异常可以用同一配置开关退回旧策略。

## 5. 页面布局建议

沿用当前导航与视觉系统，逐页收敛信息，避免为了热力图重做整套后台。

| 页面 | 第一屏优先回答 | 后续详情与操作 |
| --- | --- | --- |
| 总览 | 当前有无异常、影响哪些模型、数据是否新鲜 | 真实流量/失败/时延/容量摘要，异常卡跳转到对应筛选；静态架构说明移到帮助或折叠区 |
| 效果洞察 | 哪个模型在什么条件下变慢 | 顶部统一时间窗、来源、指标与模式；先窗口汇总，再小时矩阵，再样本和错误。静态模拟放在独立区域并保留口径标签 |
| 模型管理 | 模型是否可用、当前负载、质量依据是否充分 | 默认显示名称、状态、负载、实测时延和质量证据状态；价格、算力、能力、参数进入详情；避免固定宽表承载全部编辑功能 |
| 业务策略 | 当前生效什么、待保存改动影响什么 | 生效值/草稿有明确区分，保存前显示差异；模拟与线上效果不能共用“提升”结论；新时延策略显示关闭/影子/在线状态 |
| 质量复核 | 哪些任务缺少可靠质量证据 | 题集覆盖、失败分布、Judge 分歧、人工抽查入口；不只展示总平均分 |
| 调试工具 | 这次为什么选它、其他模型为什么没入选 | 依次呈现资格过滤、质量、成本、负载、时延证据和最终排序；一键定位相关样本，不在默认界面堆完整 JSON |

热力图保留数字与单位，颜色只辅助判断；表头和模型名适度固定，窄屏允许表内滚动。提示框要能通过键盘焦点访问。固定色阶便于前后比较，若提供自动色阶须显著注明；无数据、过期与失败使用不同文本状态。

## 6. 运营能力应形成的闭环

1. **异常闭环。** 时延上升需同时展示样本量、错误、请求长度和近期配置变化；同一异常合并，恢复后关闭。先提供后台可见事件，再按现有授权接通知渠道，不无限重复提醒。
2. **预算闭环。** 业务、重试、Judge、探测分别可计数和核对；展示实际/估算成本。优先每成功任务总成本，而非单纯追求自建占比。
3. **质量闭环。** 定期汇总覆盖不足的任务，抽样补完整候选面板；失败和难例保留。对比前冻结数据与验收标准，不用自动生成标签冒充业务真值。
4. **变更闭环。** 每次优化关联问题、变更、测试、版本、实际观测和回退方式。上线成功只说明功能交付；收益结果继续标记待验证。
5. **数据运维。** 观测日志设容量/保留边界，进程内聚合有内存上限；用原始样本重建统计时要能对账。低基数指标进入监控，高基数请求详情保留在受控日志，不把 prompt、密钥或用户标识塞进指标标签。

## 7. 分阶段路线与完成条件

| 阶段 | 交付物 | 进入下一阶段的依据 |
| --- | --- | --- |
| A：可信观测，本轮 | 分组计时、热力图、补测控制、影子评分、口径说明 | 必要测试通过，实测日志与页面一致，探测有上限，影子不影响线上选择；运行数据尚不足时明确显示 |
| B：运营闭环，后续优先 | 异常归因视图、质量证据标记、成本归属、页面列与详情收敛 | 可从异常定位到分组样本/配置；质量先验与实测清楚区分；操作与实际生效状态一致 |
| C：受控动态路由 | 替换旧时延项、小流量对照与回退记录 | 同口径证据表明目标改善且质量/费用/失败无不可接受退化；新增网关开销纳入结果 |
| D：按需容量演进 | 上游队列接入或多副本共享额度 | 先证明现有静态额度造成实际限制，再验证数据覆盖、旁路流量和故障回收；无需求不增加共享系统 |
| E：学习算法演进 | 真实业务训练与独立测试、校准、分布外回退 | 沿用离线学习隔离流程，证明相对当前 Auto 的收益，补完整路由时延；不能仅凭训练成功上线 |

持续优化按证据驱动：每轮选择一个可验证问题，完成实现与相关验收，回看实际结果，再确定下一项。优先修正会误导决策的口径，其次补可行动的运营能力，最后引入需要更多数据和维护成本的算法。这里的优先级不是无限自动扩展范围的待办授权；每轮记录本轮边界与真实完成状态。
