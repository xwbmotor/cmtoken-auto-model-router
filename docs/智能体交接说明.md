- 不要把用户曾在对话中泄露过的旧 MaaS Key 重新写入任何文件；应使用已经轮换的新 Key。
- 可读取 `.env.example` 了解变量名，但除非诊断确实需要，不要读取 `.env`。

- 默认服务只监听 `127.0.0.1`。对外开放需要 TLS、访问控制、限流和管理路径隔离。

## 5. 当前架构

```text
业务应用
  Authorization: ROUTER_ACCESS_KEY
  *** 或显式模型
        │
        ▼
Auto Router /v1/chat/completions
  1. 提取任务文本和硬能力要求
  2. 规则计算任务类型、难度和置信度
  3. 低置信度时可由语义模型复核
  4. 过滤禁用、熔断、上下文不足、能力不匹配模型
  5. 质量底线 + 自建偏好 + 成本/时延评分（成本双指标：用户侧豆价 costIndex + 平台侧资源消耗 costIndexProvider，独立权重）
  6. 灰度、会话粘性、fallback、熔断
        │
        ▼
中国移动 MaaS OpenAI-compatible API
```

可选生产组合：

```text
业务应用 → Auto Router → LiteLLM → MaaS
```

Auto Router 负责“不同模型之间选谁”；LiteLLM 负责“如何可靠调用、限流、计费和观测”。不要让两个组件同时承担同一层的模型选择，否则排障和效果归因会困难。

## 6. 关键设计决定

### 规则不是关键词首次命中即选模型

规则只产生任务类型、难度、置信度和能力约束，最终仍对所有合格候选评分。不要改成“某个关键词命中后直接指定模型”，否则容易重新出现简单题和复杂架构题难度接近的问题。

必须保持的回归行为：

- “今天星期几？”难度不高于 `0.1`。
- 长篇、多目标 MaaS Auto 路由问题难度不低于 `0.7`。
- 两者难度差至少 `0.6`。

### 低置信度才调用语义分类器

- 评估器已 provider 化：`semanticRouter.provider` 选择 `openai-chat`（MaaS 大模型分类）、`http-json`（自训练小模型 HTTP 端点，POST `{text}` 返回 `{"task","tier","complexity","confidence","reason"}`）、`cascade`（级联：先 http-json 小模型，失败或 confidence < minConfidence 升级 openai-chat 大模型，两级都挂退回规则层）或 `disabled`。
- 四种 provider 返回同一份 assessment 合同，路由主流程无感知；cascade 结果额外带 `escalatedFrom`（升级标记，metrics 的 `counters.semantic.escalated` 计数）。
- 当前 provider 为 `cascade`（v0.6.0 起）：小模型先判，置信度 ≥ `smallAcceptThreshold`(0.7) 直采；低置信升级大模型（prompt 携带小模型初判）；大模型挂降级回小模型（small-degraded），双挂才抛错回退规则层。`openai-chat` / `http-json` 可随时切换。
- v0.6.0 三阈值：`smallAcceptThreshold`（级联升级线）与 `finalAdoptionThreshold`（最终采纳线）已拆分；旧 `minConfidence` 为兼容别名（server 读 finalAdoptionThreshold ?? minConfidence ?? 0；cascade 读 smallAcceptThreshold ?? minConfidence>0 ? minConfidence : 0.7）。

### benchmark 先验与校准判定

- 质量分有两层来源，构成闭环：冷启动先验（benchmark 映射）+ 实时后验（校准判定）。
- benchmark 先验：`scripts/benchmark-to-quality.mjs` 读 `config/benchmark-data.json`（GPQA Diamond / SWE-bench / LiveCodeBench / SciCode / HLE / AA-LCR 等），按 `mapping` 折算成 `quality[task]` 初值，留痕 `models[].benchmarkScores`。只作「有据可依的起点」，不作长期评分主力。
- 可靠性判定（v0.5.4 更名：calibrationStatus → reliabilityStatus，旧字段兼容读取）：`src/calibration.mjs` 的 `shouldPromoteVerified` 依据运行时 `health` 的 successes/failures，累计样本达到 `calibration.minSamples`（默认 200）且失败率 ≤ `calibration.maxFailureRate`（默认 5%）时，`reliabilityStatus` 从 pilot/unverified 翻 verified。注意：这只证明 HTTP 可用性，不是回答质量——质量校准是独立的另一件事。
- 翻 verified 后 `router.mjs` 的 `uncertaintyPenalty` 自动归零（`reliabilityStatus === 'verified' ? 0 : 扣分`）。
- verified 是「一旦达成就持久」的状态：翻 verified 时 fire-and-forget `saveConfig` 写回 router.json，重启后仍保持。
- eval gate 实测（50 条真实用例/模型，裁判 GLM-5.3 按 rubric 打分，`config/eval-gate.json`）：deepseekv4-flash 0.908 / Qwen3.8-27B 0.920 / qwen36-35b 0.917（六维实测已写回 `quality` 并留痕 `benchmarkScores.evalGate`）。榜单先验与实测冲突时以实测为准。

### 模型选择和推理强度是两个维度

决策会给出 `off / standard / high` 推理强度建议。当前 `reasoningControl.enabled=false`，因为 MaaS 对四个模型的推理参数尚未逐一验证。

只有全局启用且单模型配置 `reasoningControl.verified=true` 时，服务才会向上游发送参数。不要未经真实调用验证就批量打开。

### 复杂任务采用更严格质量门槛

复杂任务会在全局 `qualityFloor` 上增加 `complexQualityMargin`，降低复杂任务被错发到低效果模型的概率。这体现了非对称误判成本：复杂任务低估比简单任务高估风险更大。

v0.5.1 追加两道闸门：
- **相对质量损失上限**（`routing.relQualityCap`，按 tier 分档 0.08/0.04/0.02）：候选质量低于本场最优超出容忍的直接出局，成本权重淹没质量差距的路径被封死；
- **小类分数平滑**（`routing.subtaskSmoothK=8`）：30 小类实测分按 `n/(n+k)` 平滑参与评分，防小样本偶然分错派；
- **能力 fail-closed**：tools/json/vision 未显式声明 `true` 的模型不接对应请求（chat/stream 豁免）。

记账纪律（v0.5.1）：流式成功延后到流尾判定（`markStreamOutcome` 单次落账），TTFT 独立统计；预算改为预占-结算（`BudgetTracker.reserve/settle`），结束按实际 usage 冲正，无 usage 保留估算。

### 预算是软保护和估算值

- 默认关闭。
- 必须填写真实输入/输出单价后再开启。
- 路由选择仍使用相对 `costIndex`；真实价格用于预算估算。
- 达到阈值后会增强成本倾向并降低推理强度，不会直接拒绝请求。
- 流式响应不解析最终 usage，不能把账本当成结算账单。

### Fallback 只用于 Auto

显式模型请求保持可预测性，不自动换模型。SSE 一旦已经向客户端输出，不会中途切换并重放。

## 12. 已知限制

1. 计价口径为算力豆（`budget.beansPerYuan` 换算）；预算为软保护估算值，正式计费以 MaaS 租户账单为准。
2. reasoning 参数支持按模型逐个实测验证（管理端「已验证」标记）；未验证模型不下发参数。
3. 能力字段中的 `null` 表示未知，不等于支持；工具、JSON、视觉能力仍需实测。
4. 流量、健康、语义指标仍存内存，重启丢失；决策日志已持久化；生产 Prometheus 走 `/metrics` 端点（建议设置 `METRICS_TOKEN`）。
5. 单进程内嵌无外部依赖，Windows 上 `process.kill` 的 SIGTERM 不会触发 Node 信号处理器（Windows 限制）；Docker 内核为 Linux，正常触发优雅排空，`stop_grace_period` 应大于 `SHUTDOWN_TIMEOUT_MS`（默认 30s > 20s）。
5. 预算使用估算 Token，不是 MaaS 最终账单。
6. 当前 quality 分两级校准（benchmark 先验 + eval gate 实测），但业务标注集仍是质量校准的最终依据。
7. 语义路由切换 Active 前先跑「切换影响预估」（heldout 回放），按量化门槛执行（见 docs/路由设计说明.md 第 3 节）。
8. 当前实现是单 Node 进程；多实例部署时，熔断、会话粘性、预算和指标需要迁移到 Redis/数据库。
9. 本仓库为独立 Git 仓库（GitHub 私有，面向开源分发整理中）；提交前跑 `git status` 确认范围，禁止提交父目录无关文件。

## 15. 写 Node server 行为级 e2e 测试的踩坑（v0.7.2 八审 P2-4 实测）

针对本仓库的 auto-model-router 写子进程级集成测试，按以下顺序踩过八个坑，记录如下便于后人：

1. **Windows 上 `child.kill('SIGTERM')` 不走 Node handler**：等价 TerminateProcess，子进程的 `process.on('SIGTERM', ...)` 不会被触发。POSIX CI 仍用真信号。方案：fork 子进程开 IPC（`stdio: ['ignore','pipe','pipe','ipc']`）+ 服务端 env-gated 钩子 `AMR_TEST_SHUTDOWN_IPC=1`，子进程收到 `{type:'amr-shutdown', reason:'test-ipc'}` 走同一条 `shutdownManager.shutdown(reason)`。server.mjs 内仅 5 行钩子代码（不污染生产路径）。测试断言里若 `exitCode` 是 null，多半是这个原因。

2. **手写 minimal config 会接连踩 validateConfig 必填字段**：`ownership`、`quality.default`、`latencyIndex`、`routing.mode`、`maxAttempts` 全要，否则依次抛 `'ownership 无效'`/`'quality.default 缺失'`/`'routing.mode 必须是 active 或 shadow'` 等。**直接 `structuredClone(真实 config/router.json)` 派生**，只覆盖 port/upstream/decisionLog/semanticRouter 四处。

3. **decisionLog 的字段名是 `dirPath` 不是 `dir`**：传 `dir` 会静默落到仓库默认目录（`./data/decisions/`），测试断言 `readdirSync(dataDir)` 报 ENOENT。

4. **fork 子进程走 passthrough 要 env 覆盖 UPSTREAM_BASE_URL**：派生自真实 router.json 的 cfg 仍含生产 `upstreamBaseUrl`，env 不覆盖会打到真 MaaS 401。`env: { ROUTER_KEY_MODE: 'passthrough', UPSTREAM_BASE_URL: 'http://127.0.0.1:<mock_port>', AMR_TEST_SHUTDOWN_IPC: '1', ... }`。

5. **events schema 是 writeRaw 直接写对象，无 event 字段**：测试断言不能 `e.event === 'semantic_review'`，要看 `e.v === 1 && e.requestId && e.assessment`。

6. **mock 端口要可参数化**：单测多场景（1200ms/15000ms delay）共用 `mockMaaSDelay` 函数，签名 `mockMaaSDelay(delayMs, port = PORT + 100)`，否则第二个子测试 mock 仍听 PORT+100 但 router 期望 PORT+102 报 502。

7. **Prometheus `metric(lines, name, type, help, samples)` 的 samples 必须是完整的 `name{label="val"} N` 行数组**，不能只传 label 名（会 `Cannot read properties of undefined`）。空状态用三行零值兜底（`{source="session"} 0` 等）。

8. **测试环境无 tty 触发 `stdin is not a tty`**：后台跑 `node --test` 必须 `< /dev/null`，否则 node 自身报错退出。
