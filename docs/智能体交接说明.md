## 5. 当前架构

```text
业务应用
  Authorization: ROUTER_ACCESS_KEY
  model=auto 或显式模型
        │
        ▼
Auto Router /v1/chat/completions
  1. 提取任务文本和硬能力要求
  2. 规则计算任务类型、难度和置信度
  3. 低置信度时可由语义模型复核
  4. 过滤禁用、熔断、上下文不足、能力不匹配模型
  5. 质量底线 + 自建偏好 + 成本/时延评分
  6. 灰度、会话粘性、fallback、熔断
        │
        ▼
中国移动 MaaS OpenAI-compatible API
```

可选生产组合：

```text
业务应用 → Auto Router → LiteLLM → MaaS
```

Auto Router 负责“不同模型之间选谁”；LiteLLM 负责“如何可靠调用、限流、计费和观测”。不要让两个组件同时承担同一层的模型选择，否则排障和效果归因会困难。

## 6. 关键设计决定

### 规则不是关键词首次命中即选模型

规则只产生任务类型、难度、置信度和能力约束，最终仍对所有合格候选评分。不要改成“某个关键词命中后直接指定模型”，否则容易重新出现简单题和复杂架构题难度接近的问题。

必须保持的回归行为：

- “今天星期几？”难度不高于 `0.1`。
- 长篇、多目标 MaaS Auto 路由问题难度不低于 `0.7`。
- 两者难度差至少 `0.6`。

### 低置信度才调用语义分类器

- 评估器已 provider 化：`semanticRouter.provider` 选择 `openai-chat`（MaaS 大模型分类）、`http-json`（自训练小模型 HTTP 端点，POST `{text}` 返回 `{"task","tier","complexity","confidence","reason"}`）或 `disabled`。
- 三种 provider 返回同一份 assessment 合同，路由主流程无感知。
- 分类模型当前是 `deepseekv4-flash`（openai-chat provider）。
- 默认 `semanticRouter.mode=shadow`。
- 正常线上 Shadow 分类在后台执行，不阻塞主回答。
- 管理后台单题预演会等待分类结果，以便展示差异。
- 分类失败必须安全回退规则，不得使用户请求失败。
- 实测一次分类约 2.4 秒，因此不要把所有请求都串行送去分类。

### 决策日志

- `decisionLog.enabled=true`：每次路由决策追加写入 `data/decisions/decisions-YYYY-MM-DD.jsonl`。
- 默认脱敏：用户消息只落盘角色、长度和前 160 字符，完整文本不落盘。
- 按天分文件，16MB 自动轮转，保留 14 个文件；写入失败静默计数，绝不影响请求路径。
- `GET /admin/api/decisions?count=200`（ADMIN_TOKEN）导出最近决策，`fullText=1` 时包含 head 字段。
- 用途：200~500 条标注集采集（建议下一步 #2）——每条已包含任务类型、难度、建议/实际模型、候选评分和结果。

### benchmark 先验与校准判定

- 质量分有两层来源，构成闭环：冷启动先验（benchmark 映射）+ 实时后验（校准判定）。
- benchmark 先验：`scripts/benchmark-to-quality.mjs` 读 `config/benchmark-data.json`（GPQA Diamond / SWE-bench / LiveCodeBench / SciCode / HLE / AA-LCR 等），按 `mapping` 折算成 `quality[task]` 初值，留痕 `models[].benchmarkScores`。只作「有据可依的起点」，不作长期评分主力。
- 校准判定：`src/calibration.mjs` 的 `shouldPromoteVerified` 依据运行时 `health` 的 successes/failures，累计样本达到 `calibration.minSamples`（默认 200）且失败率 ≤ `calibration.maxFailureRate`（默认 5%）时，`calibrationStatus` 从 pilot/unverified 翻 verified。
- 翻 verified 后 `router.mjs` 的 `uncertaintyPenalty` 自动归零（`calibrationStatus === 'verified' ? 0 : 扣分`）。
- verified 是「一旦达成就持久」的状态：翻 verified 时 fire-and-forget `saveConfig` 写回 router.json，重启后仍保持。
- eval gate 实测（2026-08-18）：3 个启用模型各跑 50 条真实用例（`config/eval-gate.json`），裁判模型按 rubric 打分，报告在 `data/eval-gate/`。qwen36-35b 0.847 / deepseekv4-flash 0.886 / hy3-preview 0.875。coding 维度实测结果与 SWE-bench 排序相反（DeepSeek 写代码实测最强），因此 coding 质量分以实测为准。

### 模型选择和推理强度是两个维度

决策会给出 `off / standard / high` 推理强度建议。当前 `reasoningControl.enabled=false`，因为 MaaS 对四个模型的推理参数尚未逐一验证。

只有全局启用且单模型配置 `reasoningControl.verified=true` 时，服务才会向上游发送参数。不要未经真实调用验证就批量打开。

### 复杂任务采用更严格质量门槛

复杂任务会在全局 `qualityFloor` 上增加 `complexQualityMargin`，降低复杂任务被错发到低效果模型的概率。这体现了非对称误判成本：复杂任务低估比简单任务高估风险更大。

### 预算是软保护和估算值

- 默认关闭。
- 必须填写真实输入/输出单价后再开启。
- 路由选择仍使用相对 `costIndex`；真实价格用于预算估算。
- 达到阈值后会增强成本倾向并降低推理强度，不会直接拒绝请求。
- 流式响应不解析最终 usage，不能把账本当成结算账单。

### Fallback 只用于 Auto

显式模型请求保持可预测性，不自动换模型。SSE 一旦已经向客户端输出，不会中途切换并重放。

## 12. 已知限制

1. 模型真实输入/输出价格尚未填写，预算功能暂不应启用。
2. reasoning 参数已逐一实测（2026-08-17）：档位控制均无效，minimax-m25 思考不可关闭。`reasoningControl.enabled=false` 是基于实测的正确默认值，不是待办。若未来 MaaS 支持档位参数，需重新探测。
3. 能力字段中的 `null` 表示未知，不等于支持；工具、JSON、视觉能力仍需实测。
4. 流量、健康、语义指标仍存内存，重启丢失；决策日志已持久化；生产 Prometheus 走 `/metrics` 端点（建议设置 `METRICS_TOKEN`）。
5. 单进程内嵌无外部依赖，Windows 上 `process.kill` 的 SIGTERM 不会触发 Node 信号处理器（Windows 限制）；Docker 内核为 Linux，正常触发优雅排空，`stop_grace_period` 应大于 `SHUTDOWN_TIMEOUT_MS`（默认 30s > 20s）。
5. 预算使用估算 Token，不是 MaaS 最终账单。
6. 当前 quality 分两级校准（benchmark 先验 + eval gate 实测），但业务标注集仍是质量校准的最终依据。
7. 语义路由尚无 200～500 条人工标注集，不能贸然切为 Active。
8. 当前实现是单 Node 进程；多实例部署时，熔断、会话粘性、预算和指标需要迁移到 Redis/数据库。
9. 工程目录当前位于更大的工作区中，可能尚未作为独立 Git 仓库建立提交基线。操作 Git 前先确认仓库根目录和未跟踪文件范围，禁止把父目录的无关文件一起提交。

## 13. 建议下一步

优先级从高到低：

1. 获取四个模型的真实输入价、输出价并配置预算。
2. 建立 200～500 条人工标注集，包含任务类型、难度、正确路由和回答质量。
3. 将语义 Shadow 分歧与人工标签比较，计算复杂任务低估率，而不只看总体准确率。
4. 逐模型验证工具调用、JSON、视觉和 reasoning 参数。
5. 接入 PostgreSQL/ClickHouse/Prometheus，保存路由决策、usage、TTFT、P95、错误和反馈。
6. 先 5%～10% 灰度，再逐步扩大 Auto 流量。
7. 多实例生产化时，把熔断、预算、粘性和配置状态迁移到共享状态存储。
8. 只有当内部模型明确无法满足质量底线时，再设计生态模型升级策略。

## 14. 修改代码时必须保持的原则

- 不泄露或硬编码任何 Key。
- 不删除用户已有配置历史、基准结果或无关工作区文件。
- 改动后至少运行 `node --check` 和 `npm test`。
- 修改路由算法时必须增加对应回归测试。
- 新策略默认先 Shadow，再灰度 Active。
- 任何自动降级都必须受质量底线约束。
- 页面参数要说明业务含义，避免只暴露难以理解的算法权重。
- 对模型效果的结论必须区分“已实测”“Pilot”“尚未验证”。
